# Evening Reflect 작성 지침 — 비개발자가 읽을 수 있는 말로

> 2026-10-12 CSP 결정. `outputs/daily-reflect/REFLECT_YYYY-MM-DD.md`(저녁 성찰)를 쓰는 모든 에이전트는 이 지침을 따른다.
> 이 지침은 `knowledge-management` 스킬의 `evening-reflect-protocol` 등 다른 성찰 지침보다 **문체와 구성에 관해서는 우선한다.**

## 왜 바꾸는가

저녁 성찰은 CSP가 매일 읽고, 노션에도 전시되는 글이다. 그런데 10월 성찰은 한 편이 5만 자를 넘는다. 본문은 커밋 해시와 `git` 명령, 스크립트 함수명, `S13 ⑧` 같은 내부 규칙 번호로 채워져 있다. 그래서 정작 읽어야 할 사람이 "오늘 무엇이 바뀌었고 내일 무엇을 하면 되는지"를 3분 안에 말할 수 없게 되었다. 성찰이 자기 자신에게 쓰는 일지가 되면 관찰은 정밀해지지만 독자는 사라진다. CLAUDE.md §4의 첫 원칙은 **변경 해석 가능성**이다. 해석할 수 없는 성찰은 그 원칙을 어긴다.

## 독자

**HR 17년차이고, 개발 배경이 없는 CSP.** 그리고 그가 이 글을 보여 줄 수 있는 HR 팀 동료.

판정 기준은 하나다. **이 독자가 출근길에 3분 동안 읽고 "어제 무엇이 바뀌었고, 왜 중요하고, 오늘 무엇을 하면 되는지"를 자기 말로 다시 말할 수 있는가.**

## 구성

1. **오늘의 세 줄 (맨 위, 필수).** 다음 세 문장으로 쓴다. 각 문장은 기술 용어 없이 쓴다.
   - 오늘 무슨 일이 있었나
   - 그게 왜 중요한가
   - 내일 아침 무엇을 하나
2. **본문 — 쉬운 말로 쓴 에세이 (3,000자 이내).**
   - **오늘 알게 된 것.** 최대 3개. 각각 "무엇을 봤나 → 그게 무슨 뜻인가 → 우리에게 주는 의미"의 순서로 쓴다.
   - **오늘의 의미.** 심리학·철학·조직 경험에 빗댄 성찰 한두 단락.
   - **내일 아침 할 일 (One Strategy).** 최대 3개. 누가, 무엇을, 어디서 하는지가 드러나야 한다. 사람이 결정해야 하는 일은 "CSP 확인 필요"로 표시한다.
   - **어제 예측의 결과.** 어제 예측한 것 중 맞은 것과 틀린 것을 한두 문장으로 쓴다. 표가 필요하면 3행 이내로 만든다.
3. **기술 부록 (선택, 맨 아래).** `## 기술 부록 — 검증 기록` 제목 아래에 둔다. 커밋 해시, 명령어, 파일 경로, 함수명, 승계 표(S 번호), 사전 등록, 사후 실측처럼 재현에 필요한 증거는 **전부 여기로 보낸다.** 증거를 지우라는 것이 아니라 자리를 옮기라는 것이다. 본문은 부록 없이도 이해되어야 한다.

## 말 바꾸기 표 — 본문에서는 오른쪽 말을 쓴다

| 쓰지 말 것 (본문) | 대신 쓸 말 |
| :-- | :-- |
| 커밋, commit, `c3e4f18` 같은 해시 | 저장 기록 (해시는 부록에만) |
| push, 원격에 반영 | GitHub에 올렸다 |
| 브랜치, `main`, `HEAD` | 작업 갈래, 본 줄기 |
| shallow clone, `--unshallow`, 깊이 1 | 기록의 일부만 받아 온 상태, 전체 기록을 다시 받아 옴 |
| frontmatter, `updated` 필드 | 문서 머리말 정보, "마지막 수정일" 칸 |
| cron, 23:00 job, `SYNC_OK` | 밤 11시 예약 작업, "동기화 성공" 신호 |
| `stale`, `health`, `recent_activity` | 6주 넘게 손대지 않은 문서 수, 위키 건강 점수, 최근 7일 활동량 |
| 스크립트·함수 이름 (`update_dashboard.py`, `git_last_commit_dates()`) | "계기판을 만드는 프로그램", "최근 수정일을 세는 부분" |
| `S13 ⑧`, `S34` 같은 규칙 번호 | 규칙의 내용 ("숫자 구간으로 예측하지 않기 규칙", "변화 없는 날에도 흔적 남기기 규칙") |
| 원장, heartbeat.jsonl | 매일 한 줄씩 쌓이는 기록장, 출근부 |
| 영어 약어 (CI, PR, MoM, KPI 등) | 처음 나올 때 우리말 풀이를 붙이거나 우리말로 쓴다 |

표에 없는 용어도 같은 원칙으로 판단한다. **비개발 HR 동료가 검색하지 않고 이해할 수 있는가?** 그렇지 않으면 바꾼다. 꼭 써야 하는 용어라면 처음 나올 때 괄호로 한 번 풀이한다.

## 문장 규칙

- **한 문장에는 한 가지 생각만** 담는다. 쉼표나 줄표(—)로 생각을 세 개 이상 잇지 않는다.
- **숫자는 본문 전체에서 5개 안팎**으로 줄인다. 쓸 때는 항상 의미와 함께 쓴다. 나쁜 예: "89/96 = 92.7%". 좋은 예: "날짜를 확인할 수 있는 문서 열 편 중 아홉 편이 6주 넘게 그대로다".
- **굵은 글씨는 한 단락에 한 번 이하**로 쓴다. 모든 것을 강조하면 아무것도 강조되지 않는다.
- **비유는 독자의 세계에서 가져온다.** 조직·HR·사람의 경험을 쓴다. 예: 계기판 숫자 → 근태 기록, 검증 → 면담 확인.
- **자기 비판은 짧게** 쓴다. "어제 예측이 틀렸고, 이유는 ○○였다" 한두 문장이면 된다. 같은 실수의 횟수를 세는 문장(n번째 위반)은 본문에 쓰지 않는다.
- **이전 성찰의 문체를 이어받지 않는다.** 어제 글이 어렵게 쓰였더라도 오늘 글은 이 지침을 따른다.

## 저장 전 자기 점검 (5문항, 모두 "예"여야 한다)

1. 맨 위 세 줄만 읽어도 오늘의 변화와 내일의 할 일을 알 수 있는가?
2. 본문(부록 제외)이 3,000자 이내인가?
3. 본문에 커밋 해시, 명령어, 함수명, 규칙 번호(S○○)가 하나도 없는가?
4. 본문 숫자가 모두 "그래서 무슨 뜻인지"와 함께 쓰였는가?
5. 내일 할 일 각각에 누가 하는지가 드러나는가? 사람이 결정할 일은 "CSP 확인 필요"로 표시했는가?

## 바꿔 쓰기 예시 (2026-10-11 성찰 Atom #2)

**전:**
> `stale 89` 의 분모는 122 가 아니라 **96** 이다. `updated` 필드가 없는 **26 편**은 아무리 늙어도 영원히 묵지 않는다. 계기판이 보고하는 **73%** 는 실제 **92.7%** 를 측정 불가능으로 희석한 값이다.

**후:**
> 계기판은 "오래 손대지 않은 문서가 열 편 중 일곱 편"이라고 말한다. 실제로는 열 편 중 아홉 편이다. 차이가 나는 이유는 26편의 문서에 "마지막 수정일" 칸이 비어 있기 때문이다. 계기판은 날짜를 모르는 문서를 "아직 싱싱하다"고 세고 있다. 출근 기록이 없는 직원을 "지각 없음"으로 집계한 근태표와 같다. 숫자가 거짓말을 한 것은 아니다. 다만 모르는 것을 좋은 쪽으로 세고 있었다. **내일 할 일:** 빈 칸 26편에 날짜를 채운다. 그러면 계기판 점수는 잠시 나빠 보일 수 있다. 그것이 정확해지는 과정이라는 것을 미리 알아 둔다.

노션에는 **오늘의 세 줄과 본문만** 옮긴다. 기술 부록은 옮기지 않고 "검증 기록은 GitHub 원문 참조" 한 줄과 링크로 대신한다.
