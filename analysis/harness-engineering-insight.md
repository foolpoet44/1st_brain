# Harness Engineering 인사이트

## 핵심 정의

**Harness Engineering** 이란?

> 구조를 설계하고, 맥락을 관리하고, 실행 흐름을 만들고, 검증 기준을 세우고, 반복적으로 개선하는 운영 방식

단순히 AI 도구를 다루는 기술이 아니라, **좋은 결과를 안정적으로 만들어내기 위한 구조와 설계의 문제**다.

---

## 핵심 인사이트

### 1. Harness Engineering 의 5 가지 구성 요소

| 요소          | 설명                                 | csp-brain 대응                           |
| :------------ | :----------------------------------- | :--------------------------------------- |
| **구조 설계** | 에이전트/스킬 조합, 워크플로우 설계  | `CLAUDE.md`, `.claude/rules/`, `skills/` |
| **맥락 관리** | Context, Rule, Hook 을 통한 가드레일 | `wiki/`, `projects/`, `inbox/` 폴더 구조 |
| **실행 흐름** | 작업이 진행되는 순서와 루프          | Dream Cycle, INGEST, LINT 프로토콜       |
| **검증 기준** | 결과물의 품질을 측정하는 기준        | LINT 프로토콜 (백링크, frontmatter 점검) |
| **반복 개선** | 학습과 최적화의 루프                 | Compiled Truth 갱신, 주간 다이제스트     |

---

### 2. Green Field vs Brown Field

| 구분               | Green Field             | Brown Field                   |
| :----------------- | :---------------------- | :---------------------------- |
| **환경**           | 처음부터 새로 구축      | 기존 서비스/코드베이스 유지   |
| **복잡도**         | 가벼운 구조 설계로 충분 | 복잡한 제약, 다수 팀 의사결정 |
| **AI 효과**        | 빠르게 효과 발생        | 품질/안정성 편차 큼           |
| **Harness 중요도** | 중간                    | 매우 높음                     |

**csp-brain 의 현재 위치: Green Field**

- 지금이 가벼운 구조 설계로 빠르게 효과를 볼 수 있는 시기
- 하지만 조직 확장을 위한 Brown Field 전환을 미리 준비해야 함

---

### 3. 개인 vs 조직: AI 활용의 차이

> "개인이 AI 를 잘 쓰는 것과, 조직이 AI 를 재현 가능하게 잘 쓰는 것은 전혀 다른 문제"

| 차원          | 개인        | 조직                           |
| :------------ | :---------- | :----------------------------- |
| **목표**      | 생산성 향상 | 재현 가능한 품질               |
| **필요 요소** | 팁, 단축키  | 품질, 검증, 통제, 운영, 온보딩 |
| **성공 기준** | 내가 편함   | 누구나 같은 결과               |

**시사점:**

- csp-brain 은 현재 개인용 (CSP 1 인) 으로 설계됨
- 하지만 **조직용 AI 실행력 기반**으로 확장 가능한 구조를 가져야 함
- EX Intelligence, LDS 360 등 HR SaaS 제품과의 연결 고리

---

### 4. 모델 성능보다 Harness 가 결과를 좌우한다

> "실제 현장에서는 모델의 성능 차이보다, 어떤 맥락이 주어졌는지, 어떤 흐름으로 실행되게 했는지, 어떤 기준으로 검증하는지에 따라 결과의 편차가 훨씬 크게 벌어집니다"

**증거:**

- 같은 Claude Code 를 써도 csp-brain 의 구조가 다르면 결과 품질이 다름
- `wiki/` 백링크 구조가 Graph RAG 처럼 작동함
- Dream Cycle 루틴이 지식 신선도를 보장함

│  │  - inbox/ (미가공 컨텍스트)                       │   │
│  └──────────────────────────────────────────────────┘   │

│  ┌──────────────────────────────────────────────────┐   │

│                          ▼                               │
│  ┌──────────────────────────────────────────────────┐   │
│  │  검증 기준 (Validation)                           │   │

│  └──────────────────────────────────────────────────┘   │
│                          ▼                               │
│  ┌──────────────────────────────────────────────────┐   │
│  │  반복 개선 (Iteration)                            │   │
│  │  - 주간 다이제스트로 변화 포착                    │   │

│  └──────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────┘

## 개선 제안

### 1. **검증 기준 강화** (우선순위: 상)

현재 LINT 프로토콜을 구체화:

```markdown
# LINT 체크리스트 (안)

## 구조 검증

- [ ] 백링크 0 개 문서 없는가?
- [ ] frontmatter 필수 필드 (title, created, updated, type, status) 완성인가?
- [ ] Compiled Truth 가 6 주 이상 갱신되지 않은 문서는 없는가?

## Harness 검증

- [ ] 스킬 문서가 실제 사용 가능한가? (동작 검증)
- [ ] 프로토콜이 문서화되어 있는가?
- [ ] Git 히스토리가 의미 있는 커밋 메시지를 가지는가?
```

### 2. **온보딩 문서화** (우선순위: 중)

새로운 멤버 (또는 새 AI 세션) 가 빠르게 컨텍스트를 복원할 수 있도록:

```
# CSP Brain Onboarding

## 5 분 컷 이해
1. CLAUDE.md 읽기 (2 분)
2. wiki/concepts/_index.md 스캔 (1 분)
3. projects/ README.md 확인 (2 분)

## 첫 작업 시작하기
- `ingest` — inbox 정리
- `query [질문]` — 지식 기반 답변
- `lint` — 위키 점검
```

### 3. **스킬 Harness 강화** (우선순위: 중)

`.claude/skills/` 에 다음 스킬 추가:

| 스킬            | 목적                            |
| :-------------- | :------------------------------ |
| `harness-audit` | 현재 Harness 구조 진단          |
| `context-pack`  | 세션 종료 시 컨텍스트 압축 저장 |
| `workflow-lint` | 워크플로우 정합성 점검          |

### 4. **조직 확장 준비** (우선순위: 하)

Brown Field 전환을 위한 설계:

```
# 다수 사용자 환경 대비책

## 권한 분리
- CSP (owner): wiki/ 수정, CLAUDE.md 갱신
- Team Member: inbox/ 추가, projects/ Timeline 만 수정

## 충돌 방지
- Git branch 전략: feature/inbox, feature/wiki
- PR 기반 병합 (Claude Code 가 자동 리뷰)

## 메트릭
- 주간 활성 문서 수
- 백링크 밀도 (문서당 평균 연결 수)
- Dream Cycle 준수도
```

## 핵심 교훈

> "AI 활용이 깊어질수록 중요한 것은 더 많이 시키는 것이 아니라, 더 안정적으로 잘 작동하는 환경을 만드는 것이다"

**csp-brain 이 지향해야 할 것:**

1. **안정성**: 같은 입력 → 같은 품질의 출력
2. **재현성**: CSP 가 아니더라도 같은 결과
3. **확장성**: 1 인 → 10 인 → 100 인으로 확장 가능한 구조
4. **검증 가능성**: "왜 이 결과가 나왔는가?"에 답할 수 있는 증거
