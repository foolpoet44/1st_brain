## 캐시 설계 원칙이 CSP의 워크플로우에 던지는 질문

글의 핵심 구조는 하나입니다. **프롬프트는 앞에서 뒤로 토큰 단위로 매칭된다. 앞이 바뀌면 뒤는 전부 캐시 미스.** 이것이 단순한 API 비용 문제가 아닌 이유는, CSP의 Claude Code 운영 방식이 이미 정교한 레이어 구조를 가지고 있기 때문입니다.

### 1. Ouroboros 워크플로우의 "CLAUDE.md" 위치 설계를 재점검해야 합니다

Claude Code 팀은 프롬프트 순서를 인프라처럼 다룹니다. 정적 시스템 프롬프트가 맨 앞, 그 다음이 CLAUDE.md, 세션 컨텍스트 순이며 대화 메시지는 매 턴마다 바뀌기 때문에 맨 뒤에 놓습니다.

CSP는 4레이어 폴더 아키텍처(Rules / Skills / Agents / CLAUDE.md)를 운영 중입니다. 여기서 중요한 질문이 생깁니다. **CLAUDE.md 안에 세션마다 달라지는 내용이 들어있지는 않은가?** 예를 들어 DoD 상태값, 현재 Phase, 마지막 실행 날짜 같은 것들이 CLAUDE.md에 직접 기록되어 있다면, 그것이 바뀔 때마다 캐시 접두사 전체가 날아갑니다. 글의 저자가 시스템 프롬프트에 타임스탬프 하나 넣었다가 3일치 비용을 한 시간에 날린 것과 동일한 구조입니다.

**시사점**: CLAUDE.md는 철저하게 불변(immutable) 선언 공간으로 유지해야 합니다. 세션 상태, DoD 진행도, 현재 작업 컨텍스트는 CLAUDE.md가 아니라 **대화 말미의 user message 레이어 혹은 별도 상태 파일로 주입**하는 패턴으로 전환할 필요가 있습니다.

---

### 2. `system-reminder` 패턴 — Convergence Layer 설계에 직접 적용 가능

Claude Code는 첫 요청 이후 시스템 프롬프트를 건드리지 않습니다. 바뀐 컨텍스트는 다음 사용자 메시지에 `system-reminder` 태그로 감싸서 전달합니다. 모델은 동일하게 읽지만, 캐시 접두사는 그대로 유지됩니다.

CSP가 설계한 Convergence Layer의 YAML 기반 DoD 설정과 ConvergenceCalculator는 매 턴마다 현재 상태를 계산해서 Agent에게 전달해야 합니다. 이때 그 상태를 **시스템 프롬프트 수정으로 주입하면 캐시가 깨지고, user turn의 system-reminder 태그로 주입하면 캐시가 보존됩니다.**

```python
# ❌ 캐시를 깨는 패턴
system_prompt = f"""
{base_instructions}
현재 DoD 상태: {current_dod_state}  # 매번 바뀜 → 캐시 미스
"""

# ✅ 캐시를 보존하는 패턴
system_prompt = base_instructions  # 불변

user_message = f"""
<system-reminder>
현재 DoD 상태: {current_dod_state}
Convergence Score: {score}
현재 Phase: {phase}
</system-reminder>

{actual_user_request}
"""
```

Ouroboros의 self-evolving 특성상 매 사이클마다 상태가 업데이트되는데, 그 업데이트를 어느 레이어에 주입하느냐가 비용 구조를 결정합니다.

### 3. ESCON의 도구 로딩 전략 — `defer_loading` 패턴

Claude Code 팀이 찾은 해법은 `defer_loading`입니다. 전체 도구 스키마 대신, 도구 이름과 `defer_loading: true` 플래그만 담은 가벼운 스텁을 넣습니다. 모델이 실제로 도구의 전체 스키마가 필요할 때는 `ToolSearch` 도구를 호출해서 그때그때 불러옵니다.

ESCON이 Skill Ontology를 확장하면서 연결하는 도구와 API가 늘어날수록 이 원칙이 핵심이 됩니다. 특히 RAG를 agentic SQL/Knowledge Graph 순회로 대체하는 방향을 검토 중이라면, **각 탐색 도구를 처음부터 전부 로딩하는 대신 스텁으로 등록하고 필요할 때 호출하는 lazy loading 패턴**이 캐시 보존과 비용 최적화를 동시에 달성합니다.

더 나아가면, ESCON의 Skill Graph 탐색 함수들(예: get_adjacent_skills, traverse_path, query_level_distribution 등)을 **도구 이름만 선언한 스텁 레이어 + 실제 스키마 온디맨드 로딩 구조**로 설계하면 Agent가 커질수록 오히려 비용 효율이 좋아지는 역설적 구조를 만들 수 있습니다.

---

### 4. 컨텍스트 압축과 Pulse Check 자동화 Agent의 교차점

Claude Code는 압축 호출에도 부모 대화의 시스템 프롬프트와 도구 정의를 그대로 재사용합니다. 바뀌는 것은 마지막 사용자 메시지뿐입니다(압축 지시문으로). 부모 대화의 캐시 접두사가 여전히 매칭되므로, 새 메시지와 요약 출력분만 전액 결제하면 됩니다.

Pulse Check 시스템이나 리더십 평가 Agent처럼 **장시간 실행되는 자동화 워크플로우**는 컨텍스트 윈도우 압축이 필연적으로 발생합니다. 이때 압축용 호출을 별도 시스템 프롬프트로 만들면, 그 순간이 가장 비싼 토큰(압축 직전 최대 컨텍스트)을 캐시 없이 처리하게 됩니다. **압축 지시문을 user message로만 바꾸고 시스템 프롬프트는 부모와 동일하게 유지**하면, 가장 비싼 순간에도 캐시가 작동합니다.

---

### 5. 캐시 히트율을 운영 지표로 — PathologyDetector에 추가할 항목

Claude Code 팀은 캐시 히트율을 서버 가동률처럼 모니터링합니다. 수치가 떨어지면 장애로 선언합니다.

CSP가 설계한 PathologyDetector는 현재 Stagnation, Oscillation, Repetitive Feedback, Wonder Loop 네 가지 실패 모드를 감지합니다. 여기에 **Cache Miss Spike**를 다섯 번째 pathology로 추가하는 것이 의미 있습니다. 캐시 히트율이 임계값 아래로 떨어지는 것은 단순한 비용 문제가 아니라 **워크플로우 설계가 불안정해졌다는 시그널**이기 때문입니다. 시스템 프롬프트가 의도치 않게 오염되거나, 도구 순서가 비결정적으로 바뀌거나, 세션 상태가 잘못된 레이어에 주입되고 있다는 의미입니다.

---

## 종합하면

이 글의 진짜 메시지는 **"캐시는 설계 대상이지, 자동으로 되는 것이 아니다"**입니다. CSP의 워크플로우는 이미 충분히 정교하기 때문에, 오히려 지금 시점에 이 원칙을 체계화해두는 것이 중요합니다. CLAUDE.md의 불변성 보장, 상태 주입 레이어의 명확한 분리(system vs user turn), 도구의 스텁-온디맨드 패턴, 그리고 캐시 히트율의 운영 지표화 — 이 네 가지가 CSP 워크플로우에 당장 적용할 수 있는 핵심 변환입니다.

비용 90% 절감이라는 숫자보다, **"캐시가 깨지는 순간 = 워크플로우 설계가 무너지는 순간"**이라는 관점 전환이 더 값진 통찰이라고 생각합니다.

**CSP 적용 체크** 탭은 오늘 당장 CLAUDE.md와 ESCON을 열어서 확인할 항목들입니다. 특히 빨간 ✕ 표시된 항목 — PathologyDetector에 Cache Miss Spike가 없는 것 — 은 Ouroboros 방법론의 자기완결성 측면에서 가장 빨리 추가할 수 있는 개선입니다.

**비용 시뮬레이터**는 슬라이더를 조작해보면 직감이 생깁니다. CLAUDE.md가 30,000토큰이고 세션에서 50번 호출된다면, 캐시 설계 하나가 135만 토큰 절감입니다. 세션이 길고 고정 컨텍스트가 클수록 — Ouroboros처럼 — 그 효과는 선형이 아니라 기하급수적으로 커집니다.
