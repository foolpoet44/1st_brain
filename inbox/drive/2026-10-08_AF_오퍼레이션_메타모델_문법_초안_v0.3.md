# AF 오퍼레이션 메타모델 문법 초안 v0.3

2026-10-08 · CSP

## 범위와 전제

이 메타모델은 AF 육성·인재 수급이라는 현실의 운영을 가상에서 그대로 구현하고 돌릴 수 있게 하는 문법(M2)이다. M1은 이 문법으로 기술한 AF 인재 수급 운영 모델, M0는 그 모델이 지금 돌고 있는 상태(1기 30명, 진행 중인 평가, 결정 대기 큐)다.

- 범위: 스킬 체계만이 아니라 육성·인재 수급 전체를 포괄한다('26.10.8 결정).
- 수준: 1차는 현실을 비추고 감시하는 수준으로 문법을 닫는다. 시뮬레이션용 범주는 자리만 예약한다('26.10.8 결정).
- 서사: AF가 공장에 적용하는 Process-to-Autonomy 논리를 HR 운영 자신에게 되돌린다. 현장 공정지식을 데이터화·가상화하듯, 사람의 육성·수급 운영을 데이터화·가상화한다.
- 한계: v01 실물(context.jsonld·shapes.ttl)과 아직 대조하지 않은 초안이다. 생애주기·관계·기준선 범주는 대조 후 용어와 제약을 확정한다.

## 첫 원칙: 상태는 사건에서 파생된다

모든 상태는 사건의 누적에서 계산되며, 가상 쪽에서 상태를 직접 고쳐 쓰는 경로는 없다. 판정이 원장에 기록되면 그것이 사건으로 들어오고, 후보자의 상태는 그 사건을 적용한 결과로 바뀐다. 틀린 기록은 지우지 않고 정정 사건을 새로 쌓는다.

이 원칙 하나로 세 가지가 동시에 풀린다.

- 운영 지표: 체류 시간과 병목이 사건 시각에서 자동으로 계산된다.
- 감사: 누가 언제 무엇을 근거로 바꿨는지가 남는다.
- 확장: 시뮬레이션은 같은 사건 스트림을 가상으로 흘려보내는 것으로 붙는다.

사람을 "지금 어떤 상태인가"가 아니라 "어떤 경험을 거쳐 여기에 왔는가"로 이해하는 관점을 데이터 구조로 옮긴 것이다.

## 세 개의 층: 무엇이 있는가, 어떻게 변하는가, 어떻게 아는가

10개 범주는 세 가지 질문에 나눠 답한다. 오퍼레이션 모델이 단순한 데이터베이스와 다른 지점은 세 번째 층이다. 트윈은 자기가 현실을 얼마나 정확히 알고 있는지까지 스스로 말해야 한다.

| 층 | 묻는 것 | 속한 범주 |
| :-- | :-- | :-- |
| 정적 문법 (존재론) | 무엇이 어떤 정체성으로 존재하는가 | 존재하는 것, 행위자, 관계, 기준선 |
| 동적 문법 (동역학) | 어떤 경로로, 누구에 의해, 어떤 조건에서 바뀌는가 | 생애주기, 사건, 흐름, 결정 지점 |
| 관측 문법 (인식론) | 가상이 현실을 어떻게 알고, 지금이 건강한지 어떻게 판단하는가 | 신호, 대응 |

## 문법의 구성 범주

문법은 10개 범주와 3개 예약 범주로 구성된다. 이 단계는 스킬·과목 같은 구체 클래스가 아니라 그것들을 찍어내는 틀을 정의한다.

| 범주 | 정의 | 핵심 제약 | AF 첫 인스턴스 |
| :-- | :-- | :-- | :-- |
| 존재하는 것 (Object) | 지속되는 모든 대상의 틀 | 불변 ID와 이름 분리, 생애주기 정확히 1개 선언 | 스킬, 과목, 공정 영역, 사람, 과제 |
| 행위자 (Actor) | 사람과 에이전트 | 모든 사건에 행위자 정확히 1 | 심사위원, 검증 에이전트 |
| 생애주기 (Lifecycle) | 상태·전이·전이 조건 | 전이마다 촉발 사건과 필요 권한 선언, 사건 없는 상태 변경 불가 | v01 ChangeDecision·Membership 상태 기계 |
| 사건 (Event) | 운영의 원천 데이터 | 발생 시각·기록 시각 분리, 추가만 가능 | 평가 제출, 선발 판정, 현장 투입 |
| 관계 (Link) | 상태·기간·근거를 지닌 연결의 노드화 | 상태 조건부 카디널리티 | 소속, 평가, 요구, 투입 |
| 흐름 (Flow) | 케이스가 지나는 단계·대기열·라우팅 | 체류 시간은 사건에서 계산 | Case 4종 (INTAKE·ELEMENT·PROJECT·CERT) |
| 결정 지점 (DecisionPoint) | 사람 권한이 필요한 전이 | 에이전트는 검증·추천만, 판정 불가 / andon은 진행 정지 | 선발 판정, 인증 판정 |
| 신호 (Signal) | 사건·상태에 대한 질의로 정의한 지표 | 수기 지표 금지, M0에서 계산 가능해야 함 | 미배정 0건 · 최대 체류 3일 이하 · 최근 7일 내 결정 1건 이상 |
| 대응 (Binding) | 가상 요소와 현실 원천의 연결 | 1차는 현실→가상 자동, 가상→현실 행동은 반드시 사람 경유 | 선발 원장 행, 평가 폼 응답 |
| 기준선 (Baseline) | 모델 구조·운영 상태의 시점 고정 | 해시 포함, 발행물은 특정 기준선 참조 | 172 (승인 166 · 제안 6) · sha |

예약 범주는 이름만 선언하고 제약은 걸지 않는다. 1차 설계의 어떤 결정도 이것들이 들어올 자리를 막지 않는 것이 목적이다.

- 용량 (Capacity): 강사 시수, 교육 슬롯, 사람의 가용 시간
- 시나리오 (Scenario): 운영 상태의 가상 분기
- 달력 (Calendar): 기수·분기 같은 운영 주기

## 메타클래스 명세

각 메타클래스가 반드시 가져야 하는 속성만 정의한다. 관계(LinkType)는 대상(ObjectType)의 특수형으로 둔다. 관계도 제안·승인·종료되는 생애주기를 가지며, v01의 Membership 상태 기계가 이미 그 사실을 보여준다.

| 메타클래스 | 필수 속성 | 비고 |
| :-- | :-- | :-- |
| ObjectType | ID 규칙(접두어·불변), 이름 속성, Lifecycle 참조 정확히 1 | 스킬, 과목, 공정 영역, 사람, 과제, 케이스 |
| LinkType | ObjectType 속성 + 출발·도착 타입, 상태별 카디널리티, 유효 기간, 근거 참조 | 소속, 평가, 요구, 투입 |
| ActorKind | 종류(사람·에이전트), 역할 | 권한은 개인이 아니라 역할에 붙음 |
| Lifecycle | 상태 집합, 초기·종료 상태, Transition 목록 | v01 상태 기계를 일반화 |
| Transition | 출발·도착 상태, 촉발 EventType, 필요 권한(역할 + 행위자 종류), 가드 조건 |  |
| EventType | 대상 타입, 페이로드 스키마, 촉발하는 Transition |  |
| Event | ID, 타입, 행위자, 대상, 발생 시각, 기록 시각, 페이로드, 원천 참조, 정정 대상 ID(정정 시) | 추가 전용 |
| FlowType | 케이스 타입, 단계 목록, 라우팅 규칙 | 단계 = 케이스 생애주기의 상태 |
| DecisionPoint | 대상 Transition, 사람 필수 여부, andon 여부, 필요 근거 사건 |  |
| Signal | 질의, 임계값, 심각도, 종류(운영·트윈 건강) | 신호 발생도 사건으로 기록 |
| Binding | 원천 시스템, 레코드 위치 규칙, 변환 규칙(원천 행 → 사건), 방향 | 1차는 현실→가상만 |
| Baseline | 시점, 모델 버전, 운영 상태 해시, 상태별 집계 |  |

## 정합성 규칙

메타모델의 실질은 이 규칙에 있으며, 각 규칙은 SHACL 형상으로 옮겨진다.

| 규칙 | 내용 |
| :-- | :-- |
| R1 | 모든 ObjectType과 LinkType은 생애주기를 정확히 하나 선언한다. |
| R2 | ID는 발급 후 바뀌지 않으며, 이름 변경은 사건으로만 일어난다. |
| R3 | 상태는 사건 없이 바뀔 수 없다. 모든 전이는 정확히 하나의 EventType이 촉발한다. |
| R4 | 모든 사건은 행위자 정확히 하나와 원천 참조 하나 이상을 가진다. |
| R5 | 사건은 수정·삭제되지 않는다. 오류는 정정 사건으로만 바로잡는다. |
| R6 | DecisionPoint가 붙은 전이는 사람 행위자만 촉발한다. 에이전트 사건이 촉발하면 위반이다. |
| R7 | 가상에서 현실로 나가는 행동(통보 발송, 인사 반영)은 사람 행위자의 사건을 거친다. |
| R8 | 흐름의 모든 단계는 케이스 생애주기의 상태에 대응된다. |
| R9 | 모든 신호는 사건과 파생 상태만으로 계산 가능하다. 수기 입력 지표는 정의할 수 없다. |
| R10 | 관계의 카디널리티는 양 끝 대상의 상태에 따라 달라지며, 위반은 해당 상태 진입 시점에 검사한다. |

## 실행 의미론

현재 상태는 사건 로그를 시간순으로 접어서(fold) 계산한다. 정정 사건은 원래 사건을 대체하는 방식으로 적용된다.

- 시간 두 축: 발생 시각으로 운영을 보고, 기록 시각으로 트윈의 지연을 본다. "마감 시점에 실제로 몇 명이 접수했는가"와 "그 시점에 시스템은 몇 명으로 알고 있었는가"를 구분해 답할 수 있다.
- 신호: 사건 유입 시 또는 정해진 주기로 재계산하고, 임계값을 넘으면 신호 사건을 발생시켜 같은 로그에 남긴다.

## 트윈 자신의 건강

운영 지표보다 먼저, 모델이 현실을 제대로 비추고 있는지를 확인한다. 거울이 휘어 있으면 거울에 비친 병목도 믿을 수 없다. 세 지표 모두 신호 범주의 인스턴스로 정의한다.

| 지표 | 묻는 것 | 계산 근거 |
| :-- | :-- | :-- |
| 완전성 | 현실의 모든 케이스가 가상에 존재하는가 | 원천 기록 수 대비 가상 케이스 수 |
| 지연 | 가상이 현실을 얼마나 늦게 따라오는가 | 사건의 기록 시각 − 발생 시각 |
| 일관성 | 사건으로 계산한 상태가 원천 기록과 일치하는가 | 파생 상태와 원천 값의 불일치 건수 |

## M1 예시: 선발 루프

이미 돌고 있는 선발 실행관리가 이 문법의 첫 M1 인스턴스다. 지원 한 건이 INTAKE 케이스로 생기고 아래 생애주기를 탄다.

접수(지원자 제출) → 서류 검증(에이전트 검증) → 심사(심사위원) → 판정(사람만 · 결정 지점) → 통보(문안 자동 · 발송 사람)

서류 검증은 에이전트가 수행할 수 있는 전이이고, 판정은 사람만 촉발할 수 있다. 모든 사건은 선발 원장의 행에 대응되며, 단계별 체류가 3일을 넘으면 경고한다. 체류 시간은 사건 시각에서 계산된다.

메타모델이 제대로 되어 있으면 선발 루프는 코드가 아니라 선언으로 기술된다. 아래는 축약 예시다.

```yaml
ObjectType: INTAKE_Case
  id: "INT-{기수}-{순번}"
  lifecycle: INTAKE_Lifecycle

Lifecycle: INTAKE_Lifecycle
  states: [접수, 서류검증, 심사, 판정, 통보, 종료]
  transitions:
    - 접수 → 서류검증   on: 제출완료   by: 지원자(사람)
    - 서류검증 → 심사   on: 검증통과   by: 검증에이전트 | 운영담당
    - 심사 → 판정       on: 심사완료   by: 심사위원(사람)
    - 판정 → 통보       on: 판정확정   by: 심사위원(사람)  decision: 필수
    - 통보 → 종료       on: 발송완료   by: 운영담당(사람)

Signal: 단계체류초과
  query: 현재 단계 진입 후 경과일 > 3
  kind: 운영

Binding: 선발원장
  source: 선발 원장 9시트
  rule: 판정 컬럼 변경 → 판정확정 사건
```

이 선언 하나로 체류 경고, 판정 권한 검사, 원장 감사 추적이 따라 나온다. 인증(CERT)·과제(PROJECT) 루프도 같은 문법으로 쓴다. 운영 차이를 코드 수정 없이 선언으로 바꿔 끼우는 구조가 이 메타모델의 목적이다.

## 구현 경로

v01 방식을 그대로 확장하며, 원천 시스템은 읽기만 한다.

| 층 | 형식 | 검증·실행 |
| :-- | :-- | :-- |
| M2 메타모델 | JSON-LD 컨텍스트(메타클래스·속성) + SHACL 형상(R1~R10) | pyshacl 검증 |
| M1 운영 모델 | 사람이 읽는 선언(YAML) → 변환기로 JSON-LD | M2 형상에 대고 검증 |
| M0 운영 상태 | 추가 전용 사건 로그 + 현재 상태 뷰 | 사건 fold로 상태 계산 |
| 대응 어댑터 | 원천(선발 원장 등) → 사건 변환 | 원천 수정 없음 |

## 정해야 할 것

- 관계를 대상의 특수형으로 둘지: 권장안은 예(관계도 생애주기를 가짐).
- 사건 로그 저장소: 파일 기반 JSONL로 시작해 DB로 옮길지, 처음부터 DB에 둘지.
