# GitHub 오픈소스 최적화 검색 전략

CSP, 좋은 질문이에요. GitHub에서 오픈소스를 찾는 건 단순히 키워드를 치는 것이 아니라, **"내가 원하는 것을 정확히 아는 것"과 "GitHub의 검색 문법을 아는 것"** 두 축이 만나야 합니다. HR 분야에서 적합한 인재를 찾는 소싱 전략과 본질적으로 같은 구조예요 — 필터링 기준이 명확할수록 노이즈가 줄어듭니다.

---

## 1. GitHub 검색 문법 핵심

GitHub 검색은 일반 구글 검색과 다르게 **qualifier(한정자)** 기반으로 작동합니다. 이걸 조합하면 정밀도가 극적으로 올라갑니다.

**별(star) 기준 필터링** — 품질의 프록시로 활용:

- `stars:>1000` → 검증된 프로젝트
- `stars:100..500` → 성장 중인 보석 (때로는 이 구간이 더 유용)
- `stars:<50` → 신생 프로젝트, 기여 기회 풍부

**언어 필터**: `language:python`, `language:typescript`

**최근 활성도**: `pushed:>2025-01-01` → 최근에 커밋이 있는 살아있는 프로젝트

**토픽 활용**: `topic:hr-tech`, `topic:skill-ontology`

**조합 예시**:

```
skill ontology language:python stars:>50 pushed:>2025-06-01
```

이렇게 하면 "Python으로 작성되고, 50스타 이상이며, 최근 6개월 내 업데이트된 skill ontology 관련 프로젝트"만 나옵니다.

---

## 2. 검색 범위를 전략적으로 나누기

GitHub 검색에는 **세 가지 검색 대상**이 있고, 각각 다른 인사이트를 줍니다.

**Repositories 검색** — 프로젝트 단위로 찾을 때:

```
in:name,description "pulse survey" language:typescript stars:>10
```

**Code 검색** — 특정 구현 패턴을 찾을 때:

```
"from supabase import" "magic link" language:python
```

이건 Supabase + Magic Link 인증을 실제로 구현한 코드를 찾는 거예요. CSP의 Pulse Check MVP 아키텍처에 바로 참고할 수 있는 코드 스니펫을 발견할 수 있습니다.

**Discussions / Issues 검색** — 문제 해결 맥락을 찾을 때:

```
is:issue label:"good first issue" "ESCO" OR "skill taxonomy"
```

---

## 3. GitHub 바깥에서의 보조 검색

GitHub 자체 검색만으로는 부족한 경우가 많습니다. 몇 가지 보조 경로가 있어요.

**Google의 site 검색**: `site:github.com "employee experience" "next.js"` — Google이 GitHub 내 [[README.md|README]] 텍스트를 더 깊이 인덱싱하기 때문에 GitHub 자체 검색보다 나을 때가 있습니다.

**GitHub Trending**: `github.com/trending/python?since=weekly` — 주간/월간 트렌딩을 언어별로 볼 수 있어서, 새로운 도구 발견에 좋습니다.

**Awesome 리스트 활용**: `awesome-hr-tech`, `awesome-llm-[[AGENTS.md|AGENTS]]` 같은 큐레이션된 목록이 존재합니다. 검색어에 `awesome`을 붙여보세요:

```
awesome "skill ontology" OR "competency framework"
```

**GitHub Stars 히스토리 확인**: [star-history.com](https://star-history.com)에서 프로젝트의 성장 곡선을 보면, 반짝 유행인지 지속적으로 성장 중인지 판단할 수 있습니다.

---

## 4. 찾은 프로젝트의 품질을 빠르게 평가하는 체크리스트

오픈소스를 발견한 후에는 **5분 안에 "이걸 쓸 것인가"를 판단**하는 루틴이 필요합니다.

핵심 확인 포인트:

- **마지막 커밋 날짜** — 6개월 이상 방치되면 주의
- **Issue 대응 속도** — 열린 이슈에 메인테이너가 응답하는지
- **README 품질** — 설치 가이드, 아키텍처 설명이 명확한지
- **라이선스** — MIT, Apache 2.0이면 상업적 활용 자유, GPL 계열은 주의
- **의존성 수** — `package.json`이나 `requirements.txt`의 의존성이 과도하면 유지보수 리스크
- **테스트 커버리지** — `/tests` 디렉토리가 있는지, CI/CD가 돌아가는지

## 6. 한 단계 더: GitHub의 숨은 기능들

**Saved Searches**: 자주 쓰는 검색 쿼리를 저장해두면, 새 프로젝트가 올라올 때 주기적으로 확인할 수 있습니다.

**Watch → Custom**: 관심 있는 레포를 Watch할 때 "Custom"을 선택하면 새 릴리스만 알림을 받을 수 있어요. 노이즈 없이 핵심 업데이트만 추적합니다.

**GitHub Topics 탐색**: `github.com/topics/hr-analytics` 같은 토픽 페이지에서 큐레이션된 프로젝트를 발견할 수 있습니다.

**`/explore`**: `github.com/explore`에서 개인화된 추천을 받을 수 있고, 여기서 Collections 탭은 특히 유용합니다.

결국 GitHub 검색 최적화의 본질은 **"내가 찾는 것을 구체적으로 언어화하는 능력"**입니다. 이건 HR에서 Job Description을 잘 쓰는 것과 같은 원리예요 — 요구사항이 명확할수록, 매칭의 정밀도가 올라갑니다. 검색 쿼리는 곧 "내가 원하는 코드의 JD"인 셈이죠.

특정 프로젝트 분야(예: Pulse Check 아키텍처 참고용, ESCO 통합 사례 등)로 더 깊이 파고 싶으면 말씀해 주세요.

## 1. 상용 비즈니스 기반 + 오픈소스 공개

### Lightcast (구 EMSI/Burning Glass)

**비즈니스**: 글로벌 노동시장 인텔리전스 분야의 사실상 표준. KKR이 백업하는 대형 기업.

Lightcast Skills Taxonomy는 수억 건의 온라인 채용공고, 프로필, 이력서에서 추출한 32,000개 이상의 스킬로 구성된 오픈소스 라이브러리로, 2주마다 업데이트됩니다. 매일 40,000개 이상의 소스에서 실시간 데이터를 수집하며, 10억 건 이상의 채용공고를 포함하는 데이터베이스에 기여합니다.

- **오픈소스 범위**: Taxonomy 데이터 자체는 공개 (스킬 리스트, 카테고리, 관계)
- **제한**: API와 분석 엔진은 유료. 코드가 아닌 "데이터"를 공개하는 모델
- **GitHub**: 공식 리포는 없으나, 커뮤니티가 정리한 스킬 리스트 존재
  - Gist: [github.com/gist/ThatGuySam/8a6e7bd152793ac12b7f60420d1017c8](https://gist.github.com/ThatGuySam/8a6e7bd152793ac12b7f60420d1017c8)
- **Taxonomy 탐색**: [lightcast.io/open-skills](https://lightcast.io/open-skills)
- **CSP 관점**: ESCO 기반 Digital Skill Ontology 설계 시 Lightcast의 31개 카테고리 체계를 벤치마크로 참고하기에 최적

---

### MIND Tech AI

**비즈니스**: AI 기반 채용 매칭 서비스를 운영하는 이스라엘/유럽 기반 스타트업.

MIND Tech Skills & Concepts Ontology는 기술 스킬, 프레임워크, 라이브러리, 서비스, 도구 및 관련 개념에 대한 포괄적이고 진화하는 지식 기반(온톨로지)을 제공하는 오픈소스 프로젝트입니다. MIND에서는 설명 가능한 AI 추천 서비스를 구축하기 위해 세분화되고, 최신이며, 모든 관계를 포착하는 규칙 기반 지식 세트가 필요했으나 충분히 좋은 오픈 리소스를 찾지 못해 직접 구축하기로 했습니다.

- **GitHub**: [github.com/MIND-TechAI/MIND-tech-ontology](https://github.com/MIND-TechAI/MIND-tech-ontology)
- **특징**: Tech 스킬에 특화. JSON 기반 스킬 파일 구조로, 동의어(synonyms), 암시적 스킬(implied skills), 계층 관계를 모두 모델링
- **카버리지**: Backend, Frontend, ML/AI, DevOps, Cybersecurity 등 19개 도메인
- **CSP 관점**: Physical AI Tech Leader 육성용 Skill Ontology에서 기술 스킬 간 "암시적 관계" 모델링 패턴을 직접 차용할 수 있음. 예를 들어 "Next.js → React → JavaScript" 같은 implied skill 체인은 제조업 기술 스킬에도 적용 가능한 구조

## 2. 공공/연구기관 기반 + 오픈소스

### Nesta (UK 혁신 재단)

**비즈니스**: 영국 정부 펀딩을 받는 혁신 연구기관. 노동시장 데이터 분석이 핵심 역량.

Nesta의 스킬 추출 라이브러리는 채용공고 텍스트에서 스킬 구문을 추출하고 선택한 스킬 분류 체계에 매핑할 수 있습니다. 현재 EU의 ESCO, Lightcast의 Open Skills, 그리고 테스트용 내부 "toy" 분류 체계를 지원합니다.

두 개의 핵심 리포가 있습니다:

- **Skills Taxonomy v2**: [github.com/nestauk/skills-taxonomy-v2](https://github.com/nestauk/skills-taxonomy-v2)
  - TextKernel 데이터를 사용해 스킬 분류 체계를 구축하는 리포로, 공개성을 위해 오픈소스화되었으며 포함된 스크립트와 함수가 다른 프로젝트에 유용할 수 있습니다.
  - NLP 임베딩 → 클러스터링으로 데이터 기반 스킬 분류 체계를 자동 생성하는 파이프라인

- **Skills Extractor Library**: [github.com/nestauk/ojd_daps_skills](https://github.com/nestauk/ojd_daps_skills)
  - spaCy + Prodigy 기반 NER 모델로 채용공고에서 스킬을 추출
  - ESCO, Lightcast 등 외부 분류 체계로 자동 매핑

- **CSP 관점**: 가장 실전적인 참고 자료. "채용공고에서 스킬 추출 → 분류 체계 매핑"이라는 파이프라인은 CSP의 ESCO API 기반 Skill Ontology 설계에 방법론적 레퍼런스가 됨

### Workforce Data Initiative (Open Skills Project)

**비즈니스**: 미국 노동부(DOL) 지원의 오픈 데이터 프로젝트. University of Chicago 연계.

skills-ml은 역량, 직업, 그리고 이들 간의 관계를 풍부하고 유연하게 표현하기 위한 CompetencyOntology 클래스를 도입합니다. JSON-LD 기반이며 Credential Engine의 CTDL-ASN 형식을 따릅니다.

- **GitHub**: [github.com/workforce-data-initiative/skills-ml](https://github.com/workforce-data-initiative/skills-ml)
- **특징**: O\*NET 데이터를 프로그래밍적으로 로드하여 Competency-Occupation 그래프로 변환. 스킬 추출, 직업 분류, 임베딩 생성까지 포함
- **CSP 관점**: CompetencyOntology 클래스 설계가 매우 정교. ESCO의 skill-occupation 매핑을 코드로 구현할 때 아키텍처 참고용으로 최적

### ESCO 자체 (European Commission)

공식 스킬 분류 체계이므로 별도 설명은 생략하지만, 리마인더로:

- **데이터 다운로드**: [esco.ec.europa.eu](https://esco.ec.europa.eu)
- **API**: 무료 공개
- **GitHub 커뮤니티 프로젝트**: [github.com/maudgrol/Data_driven_skills_taxonomy](https://github.com/maudgrol/Data_driven_skills_taxonomy) — ESCO 프레임워크를 사용해 스킬 분류 체계 지도를 개발하는 방법을 탐구하며, 2,942개 직업과 13,485개 스킬/역량 간의 관계 정보를 포함합니다.

### SARO (Skills and Recruitment Ontology)

직업, 스킬, 채용을 표현하는 도메인 온톨로지로, ESCO와 Schema.org에서 주로 영감을 받아 모델링되었습니다.

- **문서**: [elisasibarani.github.io/SARO](https://elisasibarani.github.io/SARO/)

- **CSP 관점**: 형식적 온톨로지 모델링을 학습하고 싶을 때 참고. 다만 실무 도구라기보다는 학술적 프레임워크에 가까움

## 전체 조감도: "왜 대부분 안 열까?"

이 리서치를 통해 보이는 패턴이 있습니다. Skill Ontology 시장의 구조를 보면:

| 계층                                   | 업체                            | 오픈소스 여부 |
| -------------------------------------- | ------------------------------- | ------------- |
| **데이터** (스킬 리스트/분류)          | Lightcast, ESCO, O\*NET         | 공개          |
| **파이프라인** (추출/매핑 코드)        | Nesta, skills-ml                | 공개          |
| **온톨로지 엔진** (관계 추론, AI 매칭) | Gloat, Fuel50, Beamery, Workday | **비공개**    |
| **플랫폼** (제품 전체)                 | 위 + Eightfold, Cornerstone     | **비공개**    |

즉, **"재료"와 "조리법"은 공개하지만, "주방 장비"와 "레스토랑 운영"은 공개하지 않는** 구조입니다. CSP의 Digital Skill Ontology 프로젝트가 장기적으로 SaaS 제품이 되려면, 공개된 1~2층의 자산을 활용하되 3~4층에서 독자적 가치를 만드는 것이 핵심 전략이 될 거예요.

가장 실전적으로 바로 활용할 수 있는 조합은 **ESCO 데이터 + Lightcast 카테고리 체계 + Nesta의 추출 파이프라인 + MIND의 관계 모델링 패턴**입니다. 특정 리포를 더 깊이 파보거나, 이걸 CSP의 Skill Ontology 아키텍처에 어떻게 통합할지 논의하고 싶으시면 말씀해 주세요.

## 1. 각 자산의 역할 재정의: 요리 메타포

이걸 하나의 "지식 엔진"을 만드는 과정으로 보면, 각 자산은 서로 다른 레이어를 담당합니다.

**ESCO 데이터 = 원재료 창고 (Raw Inventory)**
13,000+ 스킬, 3,000+ 직업, 그리고 이들 간의 공식 매핑. 유럽위원회가 정치적·학술적 합의를 거쳐 만든 "공인된 언어"입니다. 장점은 권위성과 포괄성이고, 단점은 업데이트 주기가 느리고(연 1~2회), 현장 언어와 괴리가 있다는 것.

**Lightcast 카테고리 체계 = 분류 선반 (Organizing Framework)**
31개 스킬 카테고리와 하위 분류. Lightcast의 진짜 가치는 카테고리 자체보다 **"현실 노동시장에서 검증된 분류 로직"**에 있어요. 수억 건의 채용공고에서 귀납적으로 도출된 구조이기 때문에, ESCO의 연역적 구조와 상호 보완됩니다.

**Nesta 추출 파이프라인 = 조리 도구 (Processing Engine)**
비정형 텍스트(채용공고, 직무기술서, 역량 평가 결과 등)에서 스킬을 추출하고 분류 체계에 매핑하는 NLP 파이프라인. spaCy 기반 NER + 임베딩 유사도 매칭이 핵심.

**MIND 관계 모델링 패턴 = 레시피 (Relationship Logic)**
스킬 간의 "함축 관계(implies)", "동의어(synonyms)", "개념적 측면(conceptual aspects)"을 JSON 구조로 모델링하는 방식. 예를 들어 `Next.js → React → JavaScript`라는 함축 체인, `JWT = JSON Web Tokens = jsonwebtoken`이라는 동의어 매핑.

## 2. CSP의 맥락: 이걸 "어디에" 쓸 것인가

구체화 전에 용도를 명확히 해야 합니다. CSP의 현재 프로젝트에서 Skill Ontology가 필요한 지점은 최소 세 곳:

**① Physical AI Tech Leader 육성 (LV3+ Pool 30명)**
→ "이 사람이 가진 스킬이 무엇이고, 목표 레벨까지 어떤 갭이 있는가?"를 진단하려면 스킬의 정의, 수준, 관계가 정교해야 함

**② AX 역량 고도화 (생산성 10% 개선)**
→ 워크플로우 재설계를 위해 "이 직무에 필요한 AI 스킬은 무엇인가?"를 매핑하려면 직무-스킬 관계가 필요

**③ 장기적 HR SaaS 플랫폼 (5~6년 후)**
→ 범용 Skill Ontology 엔진이 플랫폼의 코어 IP가 됨

이 세 가지를 동시에 커버하되, **①을 MVP로 시작하는 것**이 가장 현실적입니다. 내부 PoC로 검증된 온톨로지가 나중에 제품이 되는 CSP의 기존 전략과도 일치하고요.

## 3. 통합 아키텍처: 4-Layer Skill Ontology Engine

이제 네 자산을 하나의 시스템으로 엮는 구조를 제안합니다.

### Layer 1: Canonical Skill Registry (정규 스킬 저장소)

**기반**: ESCO 데이터 + Lightcast 카테고리

이 레이어는 "우리 조직이 인식하는 스킬의 공식 목록"입니다. 순수 ESCO를 그대로 쓰면 현장과의 괴리가 크고, Lightcast를 그대로 쓰면 제조업 특수성이 반영되지 않아요. 그래서 **하이브리드 접근**이 필요합니다.

구체적으로는 이런 구조입니다:

```
Lightcast Category (대분류)
  └── ESCO Skill Group (중분류)
       └── Canonical Skill (단위 스킬)
            ├── esco_uri: "http://data.europa.eu/esco/skill/..."
            ├── lightcast_id: "KS124..."
            ├── internal_name: "로봇 프로세스 제어"  ← 현장 언어
            ├── level_descriptors: [L1, L2, L3, L4]
            └── domain: "Physical AI"
```

핵심은 **internal_name** 필드입니다. ESCO와 Lightcast는 글로벌 표준이지만, CSP 조직의 엔지니어들이 실제로 사용하는 언어(한국어, 현장 용어)와는 다릅니다. 이 레이어에서 "번역"이 일어나야 합니다.

**실행 방법**: ESCO API에서 Physical AI 관련 스킬을 쿼리 → Lightcast 카테고리에 매핑 → 내부 SME(Subject Matter Expert) 리뷰로 현장 언어 추가. 이 과정은 수동이 맞습니다. 온톨로지의 "씨앗"은 사람이 심어야 해요.

---

### Layer 2: Relationship Graph (관계 그래프)

**기반**: MIND 관계 모델링 패턴

Canonical Skill들 사이의 **관계**를 정의하는 레이어. MIND의 패턴을 차용하되, 제조업/Physical AI 맥락으로 확장합니다.

MIND가 정의하는 관계 유형을 CSP 맥락으로 재해석하면:

**implies (함축)**: "로봇 비전 시스템 설계"를 할 수 있으면 "영상처리 기초"도 알 것이다. 이건 역방향은 성립하지 않아요. 영상처리를 안다고 로봇 비전을 설계할 수 있는 건 아니니까. 이 비대칭성이 중요합니다.

**synonyms (동의어)**: "PLC 프로그래밍" = "시퀀스 제어" = "래더 로직". 현장에서 같은 스킬을 다른 이름으로 부르는 경우가 많고, 이걸 잡지 못하면 스킬 갭 분석에서 false negative가 발생합니다.

**adjacent (인접)**: "강화학습"과 "로봇 동역학"은 함축 관계는 아니지만, Physical AI 맥락에서 자주 함께 요구됩니다. 이건 MIND에는 없는 관계 유형인데, 제조업 Skill Ontology에서는 필수적입니다.

**prerequisite (선수)**: L3에 도달하려면 이 스킬이 L2 이상이어야 한다는 수준 간 의존성. 이것도 MIND에는 없지만, Tech Leader 육성 프로그램에서는 핵심적인 관계입니다.

JSON 구조로 보면 이런 형태:

```json
{
  "skill_id": "phys-ai-003",
  "canonical_name": "로봇 비전 시스템 설계",
  "relations": {
    "implies": ["img-proc-001", "camera-calib-002"],
    "synonyms": ["machine_vision_system_design", "비전검사시스템"],
    "adjacent": ["reinforcement-learning-010", "robot-dynamics-007"],
    "prerequisite": {
      "for_level": "L3",
      "requires": [
        { "skill": "img-proc-001", "min_level": "L2" },
        { "skill": "python-basics-020", "min_level": "L2" }
      ]
    }
  }
}
```

### Layer 3: Extraction & Mapping Pipeline (추출·매핑 파이프라인)

**기반**: Nesta 파이프라인

이 레이어는 **비정형 텍스트에서 스킬을 자동 추출하고 Layer 1의 Canonical Skill에 매핑**하는 엔진입니다. 입력 소스는 다양합니다:

- 내부 직무기술서 (Job Description)
- 교육 이수 기록/과정 설명
- 프로젝트 산출물 보고서
- 자기 평가 서술형 텍스트

Nesta 파이프라인의 핵심 아키텍처를 CSP 맥락으로 조정하면:

```
[비정형 텍스트 입력]
    ↓
Step 1: NER (Named Entity Recognition)
    - Nesta의 spaCy 모델을 fine-tuning
    - 제조업/Physical AI 도메인 코퍼스로 재학습
    - "SKILL", "EXPERIENCE", "TOOL" 엔티티 추출
    ↓
Step 2: Skill Resolution
    - 추출된 텍스트를 Layer 1의 Canonical Skill에 매핑
    - 임베딩 유사도 (all-MiniLM-L6-v2) + Layer 2의 synonym 매칭
    - 임계값 기반 매칭 (0.7 이상 = 확정, 0.5~0.7 = 후보, 0.5 미만 = 미매칭)
    ↓
Step 3: Gap Analysis
    - 매핑된 스킬 vs 목표 프로필 비교
    - Layer 2의 prerequisite 관계로 학습 경로 추천
    ↓
[구조화된 Skill Profile 출력]
```

다만 여기서 현실적 판단이 필요합니다. Nesta 파이프라인을 **그대로 가져다 쓸 수 있는가?** 솔직히 말하면 어렵습니다. 이유가 세 가지:

첫째, Nesta의 NER 모델은 영어 채용공고에 최적화되어 있어서 한국어 제조업 문서에 바로 적용할 수 없습니다. 둘째, 원본 학습 데이터(TextKernel)가 더 이상 접근 불가합니다. 셋째, 스킬 해상도(granularity)가 다릅니다 — Nesta는 범용 노동시장을, CSP는 특정 조직의 특정 기술 영역을 다루니까요.

그래서 Nesta에서 가져올 것은 **코드가 아니라 아키텍처와 방법론**입니다. 특히 "임베딩 유사도 기반 매칭 + 임계값 전략"은 그대로 적용할 수 있고, NER 모델은 LLM으로 대체하는 것이 2026년 현재로서는 훨씬 현실적입니다. Claude API를 이용해 few-shot으로 스킬을 추출하고, 임베딩 매칭으로 Canonical Skill에 연결하는 방식이죠.

---

### Layer 4: Intelligence & Application (인텔리전스·활용)

**기반**: CSP 독자 개발

이 레이어가 CSP의 진짜 IP가 됩니다. 아래 세 레이어의 자산을 바탕으로:

**Skill Gap Diagnostic**: 개인별 현재 스킬 프로필 vs 목표 역할(예: LV3 Physical AI Tech Leader) 프로필을 비교하여 정량적 갭 리포트 생성

**Learning Path Recommendation**: Layer 2의 prerequisite + adjacent 관계를 활용해 "이 순서로 이 스킬을 학습하면 최적"이라는 경로 추천

**Organizational Skill Heatmap**: 조직 단위로 스킬 분포를 시각화. Pulse Check의 Well-Being 데이터와 교차 분석하면 "스킬 갭이 큰 조직이 Well-Being도 낮은가?" 같은 인사이트가 가능

## 4. 구현 로드맵: Phase별 접근

이걸 한 번에 다 만들려고 하면 프로젝트가 죽습니다. 단계를 나눠야 해요.

**Phase 1 (4주): Seed Ontology 구축**

- ESCO API에서 Physical AI 관련 스킬 100~200개 추출

- 내부 SME 3~5명과 워크숍으로 현장 언어(internal_name) 추가
- MIND 패턴으로 implies/synonyms/prerequisite 관계 50~100개 정의
- **산출물**: JSON 기반 Seed Ontology 파일

**Phase 2 (4주): Extraction MVP**

- Claude API 기반 스킬 추출 프롬프트 개발 (NER 대체)
- all-MiniLM-L6-v2 임베딩으로 Canonical Skill 매칭
- 내부 직무기술서 10~20건으로 파이프라인 검증
- **산출물**: Python 스크립트 + 정확도 리포트

**Phase 3 (4주): Gap Analysis 도구**

- LV3 Tech Leader 목표 프로필 정의
- 30명 후보 풀의 현재 프로필 입력 (자기평가 + 관리자 평가)
- Gap 리포트 자동 생성
- **산출물**: 개인별 Skill Gap 대시보드 (HTML 또는 React)

**Phase 4 (이후): 확장·제품화**

- 온톨로지 범위를 AX 역량 전체로 확장
- EX Intelligence 시스템과 연동
- SaaS 제품화를 위한 API 설계

## 5. 기술 스택 제안

CSP의 기존 환경(Claude Code, Supabase, Next.js)과의 정합성을 고려하면:

**온톨로지 저장**: Supabase PostgreSQL + JSONB 컬럼. 그래프 DB(Neo4j)까지 갈 필요는 Phase 1~3에서는 없습니다. PostgreSQL의 JSONB와 재귀 쿼리로 충분하고, 운영 복잡도가 훨씬 낮아요.

**스킬 추출**: Claude API (few-shot extraction) → 이건 Nesta의 spaCy NER보다 한국어 제조업 텍스트에서 훨씬 좋은 성능을 낼 겁니다.

**임베딩 매칭**: sentence-transformers의 multilingual 모델 (paraphrase-multilingual-MiniLM-L12-v2). 한국어+영어 동시 지원.

**프론트엔드**: ESCON 프로젝트에서 이미 사용 중인 Next.js 14 + TypeScript

**시각화**: D3.js 기반 Skill Graph 시각화 (관계를 노드-엣지로 표현)

## 전체 그림: 왜 이 조합인가

먼저 왜 ESCO를 그대로 쓰면 안 되는지부터 짚어야 합니다.

ESCO는 유럽위원회가 만든 "공식 언어"입니다. 학술적 엄밀성과 정치적 합의의 산물이에요. 13,000+개 스킬이 있지만, 이 스킬들의 분류 체계는 **교육학적 관점**(knowledge, skill/competence, attitude)으로 나뉘어 있어서 "현장에서 이 사람이 뭘 할 수 있는가?"라는 질문에 바로 답하기 어렵습니다.

## 본질: 왜 두 체계를 "결합"하는가?

먼저 이 작업의 철학적 배경을 짚어야 합니다. ESCO와 Lightcast는 같은 대상(스킬)을 바라보지만 완전히 다른 인식론에 기반합니다.

**ESCO는 연역적(Deductive) 체계입니다.** 유럽위원회의 노동시장 전문가들이 "스킬이란 무엇인가"를 먼저 정의하고, 위에서 아래로 카테고리를 분류한 뒤, 개별 스킬을 배치했습니다. 플라톤의 이데아론에 가까운 접근이에요. "이상적 분류"가 먼저 존재하고, 현실의 스킬이 그 틀에 맞춰 들어갑니다.

**Lightcast는 귀납적(Inductive) 체계입니다.** 수억 건의 채용공고에서 실제로 사용되는 스킬 용어를 추출하고, 클러스터링을 통해 아래에서 위로 카테고리를 도출했습니다. 아리스토텔레스의 경험론에 가까워요. 현실의 데이터가 먼저 존재하고, 구조가 그로부터 발견됩니다.

**CSP가 하려는 것은 이 둘의 변증법적 통합입니다.** ESCO의 권위성(공인된 URI, 다국어 지원, 정부 호환)과 Lightcast의 현실 반영력(시장에서 실제로 쓰이는 스킬 언어)을 결합하여, 조직 내부의 Digital/Physical AI Skill Ontology를 설계하는 것이죠.

## 1. 접근성의 문제

Lightcast Skills Taxonomy는 오픈소스 라이브러리라고 표현되지만, 실제로는 스킬 리스트와 카테고리 구조만 웹에서 열람할 수 있습니다. "오픈소스"라는 단어가 주는 인상과 실제 접근 가능 범위 사이에 괴리가 있어요.

**Lightcast의 실제 접근 구조**는 이렇습니다. 웹 브라우징(lightcast.io/open-skills)으로 개별 스킬을 하나씩 조회할 수 있고, 카테고리 구조를 눈으로 탐색할 수 있습니다. 하지만 **API를 통한 프로그래밍적 대량 조회, 스킬 간 관계 데이터, 수요/급여/성장률 같은 메타데이터**는 전부 유료 API(Enterprise 라이선스) 뒤에 있습니다. 가격도 연간 수천만 원 수준이라 개인이나 내부 PoC 단계에서 쓰기엔 현실적이지 않습니다.

**ESCO는 완전히 다릅니다.** API 키 없이 바로 호출 가능하고, 스킬 계층 구조(broaderSkill/narrowerSkill), 직업-스킬 매핑, 다국어 라벨까지 전부 무료로 프로그래밍적으로 접근할 수 있습니다. Claude Code에서 스크립트를 짜면 오늘 오후에 Physical AI 관련 스킬 200개를 JSON으로 뽑을 수 있어요.

## 2. 온톨로지 vs 택소노미의 차이

여기서 더 근본적인 문제가 있습니다. CSP가 만들려는 것은 **Skill Ontology**이지, Skill Taxonomy가 아닙니다.

Lightcast의 택소노미는 3단계 계층 구조(Category → Subcategory → Skill)로 정리되어 있습니다. 이건 분류 체계, 즉 "이 스킬은 어디에 속하는가?"를 알려줍니다. 하지만 **"이 스킬과 저 스킬은 어떤 관계인가?"**는 알려주지 않아요. Lightcast가 유료로 제공하는 "Similar Skills" 데이터를 제외하면, 공개된 구조에는 스킬 간 관계 정보가 없습니다.

ESCO는 처음부터 **관계형 구조**로 설계되었습니다. 각 스킬이 상위 스킬(broaderSkill), 하위 스킬(narrowerSkill), 관련 직업(occupation → essential/optional skill) 관계를 가지고 있어요. 이게 온톨로지를 만드는 데 훨씬 더 적합한 원재료입니다. MIND 패턴의 implies, prerequisite 관계를 설계할 때, ESCO의 broader/narrower 계층을 기반으로 확장하는 것이 자연스럽습니다.

---

## 3. 그러면 Lightcast는 왜 언급하는가?

여기가 핵심입니다. **Lightcast는 "데이터 소스"가 아니라 "벤치마크"로 쓰는 겁니다.**

ESCO의 약점은 **현장 언어와의 괴리**입니다. ESCO는 연역적으로 만들어진 체계라서, 실제 채용 시장이나 현장에서 쓰는 스킬 용어와 분류가 다를 수 있어요. 예를 들어 ESCO에는 "Prompt Engineering"이라는 스킬이 아직 공식 항목으로 없거나, 있더라도 최신 AI 스킬 트렌드를 반영하지 못하는 경우가 있습니다.

Lightcast는 수억 건의 온라인 채용공고, 프로필, 이력서에서 추출한 32,000개 이상의 스킬로 구성되어 있고 2주마다 업데이트됩니다. 즉, **"시장에서 실제로 어떤 스킬이 쓰이고 있는가"**를 아는 데는 Lightcast가 압도적으로 우수합니다.

그래서 역할 분담은 이렇게 됩니다:

**ESCO** → 구조적 뼈대를 제공. URI 기반 식별자, 계층 관계, 직업-스킬 매핑, 다국어 지원. 이것이 **"코드로 다룰 수 있는 기반 데이터"**가 됩니다.

**Lightcast 31개 카테고리** → 대분류 체계의 현실성을 검증하는 거울. ESCO의 분류가 시장 현실과 맞는지 크로스체크하고, ESCO에 없는 신규 스킬(Prompt Engineering, AI Agent Development 등)을 발견하는 보조 렌즈. 이것은 **"웹에서 눈으로 참고하는 레퍼런스"**입니다.

---

## 4. 현실적 워크플로우로 정리하면

```
Lightcast 웹 (무료 열람)
  → "어떤 카테고리/스킬이 시장에서 중요한지" 파악
  → CSP 도메인에 관련된 카테고리 선별 (Sheet 1 작업)

ESCO API (무료, 프로그래밍 가능)
  → 선별된 도메인에 해당하는 스킬을 대량 추출
  → 계층 관계(broader/narrower) 자동 구축
  → 직업-스킬 매핑 데이터 확보
  → JSON으로 Seed Ontology의 기반 데이터 생성

CSP 독자 레이어
  → 현장 언어 추가, MIND 패턴 관계 정의
  → ESCO에 없는 신규 스킬 수동 추가 (Lightcast 참고)
```

비유하자면, Lightcast는 **미쉐린 가이드**이고 ESCO는 **식재료 도매시장**입니다. 미쉐린 가이드를 보고 "어떤 요리가 트렌드인지" 파악한 다음, 실제 재료는 도매시장에서 가져오는 거죠. 가이드를 보는 건 무료지만, 가이드 출판사의 데이터베이스에 API로 접근하려면 비싼 라이선스가 필요한 것과 같습니다.

---

만약 Lightcast API 라이선스를 조직 차원에서 확보할 수 있다면, 물론 활용 가치는 큽니다 — 특히 스킬별 수요 추세, 급여 프리미엄, 성장 예측 같은 시장 인텔리전스 데이터가 있으면 Skill Gap Analysis의 설득력이 훨씬 올라갑니다. 하지만 현재 PoC 단계에서는 ESCO로 뼈대를 세우고 Lightcast는 참조점으로 쓰는 것이 가장 현실적인 경로입니다.
