## ESCON에 하네스를 입힌다는 것의 진짜 의미

이미지의 핵심 명제는 단순합니다. **Agent = Model + Harness**. 그리고 벤치마크 사례가 보여주듯, 모델을 바꾸지 않고 하네스만 정교하게 설계해도 52.8% → 66.5%의 성능 도약이 가능합니다. ESCON에 대입하면, LLM을 교체하는 것보다 ESCON 고유의 하네스를 설계하는 것이 훨씬 빠르고 실용적인 경로입니다.

과거 논의에서 4레이어(Context Shell / Workflow Engine / Domain Membrane / Output Contract)를 설계했다면, 이번 이미지는 그 위에 **미들웨어 훅**과 **Eval-BETTER 루프**라는 두 축을 추가로 요구하고 있습니다.

---

## 제안 1 — 미들웨어 훅 3개를 ESCON 언어로 재정의

이미지의 `before_agent`, `before_model`, `wrap_model_call`은 추상적인 훅 이름입니다. ESCON에서는 이것을 도메인 언어로 재명명하고 구체적인 책임을 부여해야 합니다.

**`escon_before_agent` → SkillContextLoader**

에이전트가 작동하기 전에, 요청 사용자의 현재 스킬 레벨 데이터를 Supabase에서 조회하고, 관련 Ontology 노드 클러스터를 메모리에 적재합니다. "나 AI 쪽으로 가고 싶은데"라는 자연어가 들어오는 순간, 이미 시스템은 `skill_nodes → AI/ML 클러스터 → LV3 요구 역량` 맵을 준비해두는 겁니다. 이게 없으면 LLM은 일반적인 AI 공부 조언을 생성할 뿐, ESCON만의 Ontology 기반 응답을 줄 수 없습니다.

**`escon_before_model` → GapHeuristicsInjector**

LLM을 호출하기 직전, 갭 분석 판단 기준을 동적으로 주입합니다. "갭 2레벨 이상이면 멘토링 우선", "6개월 내 달성 불가이면 단계 분리", "현재 프로젝트 미연결 스킬이면 우선순위 하향" — 이 세 가지 Heuristics를 매 호출마다 컨텍스트에 삽입합니다. 정적 시스템 프롬프트가 아니라, 사용자 상황에 맞게 **동적으로** 주입하는 것이 핵심입니다.

**`escon_wrap_model_call` → OutputContractValidator**

LLM 응답이 돌아온 뒤, Output Contract 스키마에 맞는지 검증합니다. `current_level`, `target_level`, `gap_score`, `priority_skills(max 3)`, `timeline_estimate` — 이 5개 필드가 모두 존재하고 유효한 범위인지 체크하고, 위반 시 재생성 요청을 자동 발행합니다. 이것이 이미지의 `PreCompletion` 개념과 정확히 대응합니다.

---

## 제안 2 — ESCON 전용 Eval 체계

이미지의 "More evals ≠ Better agents"라는 명제가 핵심입니다. Eval을 쌓는 게 목적이 아니라, **행동을 바꾸는 벡터**로서의 Eval이어야 합니다. ESCON에서는 두 축으로 분리해야 합니다.

**정답률(Correctness) Eval**: 갭 분석 결과가 실제 역량 데이터와 일치하는가. 검증 방법은 HR 전문가의 수동 레이블링 30건을 기준 데이터셋으로 구성하고, LLM 출력과 비교하는 것입니다.

**경로 효율(Efficiency) Eval**: 추천된 학습 경로가 6개월 내 실행 가능한가. 검증 방법은 추천 경로의 총 학습 시간을 추산하고, 현실적 업무 부하와 교차 검증하는 것입니다.

두 Eval이 모두 통과한 케이스만 Regression Test로 전환해서 ESCON Harness의 DoD 체크포인트로 고정합니다. 이것이 이미지 섹션 5의 LangSmith 자동 모니터링에 해당하는 ESCON 버전입니다.

---

## 제안 3 — BETTER 루프를 Ouroboros에 통합

이미지의 하네스 자동 개선(BETTER) 구조는 CSP가 이미 설계한 Ouroboros 방법론과 정확히 같은 철학입니다. 다만 Ouroboros가 자기 진화 사이클을 추상적으로 다룬다면, BETTER는 그것을 **Eval → Failure Trace → Harness 변경 제안 → 검증** 의 구체적 루프로 구현합니다.

실천적 적용 방안은 이렇습니다. ESCON에서 OutputContractValidator가 검증 실패를 기록할 때마다, 실패 패턴을 분류합니다. 필드 누락인지, 레벨 범위 초과인지, 우선순위 스킬 초과인지. 이 패턴이 3회 이상 반복되면 GapHeuristicsInjector의 프롬프트 수정을 자동 제안하는 로직을 추가합니다. 수동으로 검토 후 승인하면 하네스가 업데이트되고, 통과한 케이스는 Regression Test로 고정됩니다. 이것이 ESCON의 자기 개선 루프입니다.

---

## 구현 우선순위 — 3단계 로드맵

지금 당장 모든 것을 구현할 필요는 없습니다. 이미지의 학습 로드맵(Anatomy → Improving → Middleware → Evals → Better)을 ESCON에 적용하면 이런 순서가 됩니다.

**Phase 1 (이번 달)**: SkillContextLoader 구현. 가장 즉각적인 효과를 내는 훅입니다. Supabase에서 사용자 스킬 데이터를 에이전트 진입 전에 조회하는 `before_agent` 훅만 붙여도, LLM 응답의 도메인 적합도가 눈에 띄게 달라집니다.

**Phase 2 (다음 달)**: OutputContractValidator + 기초 Eval 2건(Correctness / Efficiency). Output Contract 없이는 Eval을 정의할 수 없고, Eval 없이는 하네스 개선 방향을 잡을 수 없습니다.

**Phase 3 (2분기)**: BETTER 루프 통합. 실패 Trace 자동 분류 → 하네스 수정 제안 → Regression Test 자동화.

---

결국 이미지가 CSP에게 말하는 것은 하나입니다. ESCON은 지금 "모델이 있는 시스템"이지, "하네스가 있는 에이전트"가 아닙니다. SkillContextLoader 하나를 붙이는 순간부터, ESCON은 Ontology 뷰어에서 진짜 에이전트로 전환되기 시작합니다. 그 첫 훅을 이번 주 안에 구현하는 것이 제가 드리는 가장 실용적인 제안입니다.

## 이제 ESCON에 붙이는 순서

**Step 1 — 패키지 설치** (터미널에서)

```bash
npm install @anthropic-ai/sdk @supabase/supabase-js
```

**Step 2 — 파일 3개를 ESCON 프로젝트에 복사**

```
skillContextLoader.ts → src/lib/
route.ts              → src/app/api/chat/
ChatWidget.tsx        → src/components/
```

**Step 3 — `.env.local`에 키 추가**

```
ANTHROPIC_API_KEY=sk-ant-...
```

(Supabase 키는 이미 있을 거예요)

**Step 4 — 원하는 페이지에 한 줄 추가**

```tsx
<ChatWidget userId="user-123" />
```
