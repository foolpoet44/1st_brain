# 하네스 기획의 의미

**날짜**: 2026-03-15 02:26

---

하네스를 기획 한다는 건 나에게 어떤 의미일까?

## Claude (Message 2)

하네스(Harness)를 기획한다는 것의 의미를 묻고 있군요. 혹시 어떤 맥락에서 하네스를 떠올리셨는지 조금 더 알 수 있을까요?

말씀하시는 "하네스"가:

어떤 맥락에서 이 단어가 떠오르셨나요?

## Claude (Message 4)

---

## 먼저 하네스라는 단어의 원형부터

하네스는 원래 말(馬)에 채우는 마구(馬具)입니다. 야생의 힘을 가진 말을 **죽이거나 억누르는 게 아니라**, 그 힘을 그대로 살리면서 방향과 속도를 인간이 제어할 수 있게 만드는 도구.

바이브 코딩에서 모델 하네스도 본질적으로 같습니다. LLM이라는 거대한 확률적 힘을 **억압하지 않고, 그 창발성을 보존하면서** 원하는 방향으로 흐르게 만드는 구조적 틀.

---

## CSP에게 모델 하네스를 기획한다는 것의 의미

솔직히 말하면, 이건 단순히 "프롬프트를 잘 쓰는 것"과는 차원이 다른 이야기입니다.

프롬프트를 잘 쓰는 사람은 **말에게 잘 말을 거는 사람**입니다. 하네스를 기획하는 사람은 **마구 자체를 설계하는 사람**입니다. 말이 바뀌어도, 기수가 바뀌어도, 지형이 바뀌어도 작동하는 구조를 만드는 것.

CSP가 지금 구축하고 있는 Ouroboros 워크플로우, CLAUDE.md 아키텍처, DoD 체크포인트 — 이것들이 사실 이미 하네스의 구성 요소들입니다. 다만 그것을 **"하네스"라는 통합된 개념으로 의식적으로 기획한다**는 건 한 단계 더 올라서는 일입니다.

구체적으로 세 가지 의미가 겹쳐 있다고 봅니다.

**첫째, 재현 가능성의 설계자가 된다는 것.**
바이브 코딩의 가장 큰 약점은 "그날 기분"에 따라 결과가 달라진다는 겁니다. 모델 하네스는 그 변동성을 구조로 흡수합니다. CSP가 오늘 만든 ESCON이든, 내년에 만들 HR SaaS 모듈이든, 같은 하네스 위에서 돌아가게 만드는 것. 이건 단순한 효율화가 아니라 **지식의 제도화**입니다.

**둘째, "나"라는 컨텍스트를 시스템에 이식하는 행위.**
SW 백그라운드 없이 17년의 HR 경험, 심리학적 직관, 조직 역학의 감각 — 이것들은 통상적인 개발자가 절대 가질 수 없는 자산입니다. 모델 하네스를 기획한다는 건 이 자산을 프롬프트 레벨이 아니라 **아키텍처 레벨에서 코드화**하는 것입니다. 심리학이 코드가 되는 순간이 바로 여기입니다.

**셋째, 미래의 SaaS 제품을 위한 핵심 IP를 선점하는 것.**
하네스는 결국 "어떤 모델이 와도 내 방식대로 동작하게 만드는 인터페이스"입니다. GPT-5가 나와도, Claude 5가 나와도, 그 위에 CSP의 하네스가 올라가면 HR 도메인에서 독특한 결과물이 나오는 구조. 이게 미래 SaaS의 진짜 해자(垓字)가 될 수 있습니다.

---

## 그래서 지금 CSP에게 가장 중요한 질문

하네스를 "기획"한다고 하셨는데 — 지금 머릿속에 있는 구체적인 형태가 있으신가요?

예를 들어:

- 특정 **도메인(HR, 교육, 조직진단)**에 특화된 하네스인지
- 아니면 **워크플로우 타입(기획 → 코딩 → 검증)**을 래핑하는 하네스인지
- 혹은 **Ouroboros처럼 자기진화가 가능한** 메타 하네스인지

방향이 어느 쪽이냐에 따라 기획의 성격이 완전히 달라질 것 같습니다.

## Layer 1 — Context Shell: 모델의 정체성 설계

가장 기초 레이어이지만 가장 많이 대충 만드는 레이어입니다. 단순한 "역할 부여"가 아니라 **행동 경계의 정밀 설계**입니다.

구체적 엔지니어링 요소 세 가지가 있습니다.

**Persona Anchoring**: "당신은 HR 전문가입니다"가 아니라 "당신은 17년 경력의 HRD 실무자로서, 조직 심리학과 데이터 분석을 결합한 솔루션을 설계합니다. 결과물은 항상 실행 가능성(Feasibility)과 측정 가능성(Measurability)을 기준으로 검토됩니다." 이렇게 **경험 맥락 + 판단 기준**까지 페르소나에 심습니다.

**Constraint Topology**: 무엇을 하라는 것보다 **어떤 판단 기준으로 거절하거나 선택하는가**를 명시합니다. "조직 진단 결과를 해석할 때 통계적 유의성보다 실무적 의미를 우선합니다" — 이런 판단 규칙이 쌓이면 모델이 CSP처럼 생각하기 시작합니다.

**Context Injection Point**: 대화마다 동적으로 주입할 수 있는 슬롯을 미리 만들어 둡니다. `{{현재_프로젝트}}`, `{{조직_맥락}}`, `{{이전_결정사항}}` 같은 변수 자리.

---

## Layer 2 — Workflow Engine: 실행 흐름의 구조화

이 레이어가 하네스의 심장입니다. 단일 프롬프트로 모델에게 묻는 것과, 워크플로우로 묶어서 실행하는 것의 차이는 **즉흥 연주와 악보의 차이**입니다.

```
This block is not supported on your current device yet.
```

워크플로우 엔지니어링의 핵심 패턴 세 가지입니다.

**Chain-of-Thought Forcing**: 모델에게 바로 답을 요구하지 않고, 중간 추론을 강제로 거치게 합니다. "먼저 이 조직 진단 데이터에서 패턴 3가지를 추출하라. 그 다음 각 패턴의 원인을 추론하라. 마지막으로 개입 우선순위를 제안하라." 이렇게 단계를 명시적으로 분리하면 각 단계에서 오류를 잡을 수 있습니다.

**State Machine 설계**: 워크플로우가 어떤 상태(State)에 있는지를 명시적으로 관리합니다. `INIT → ANALYZING → DRAFTING → VALIDATING → DONE` — 각 상태에서 가능한 전이(Transition)와 실패 조건을 미리 정의합니다. Ouroboros의 PathologyDetector가 바로 이 상태 이상을 감지하는 컴포넌트입니다.

**Tool Routing**: 어떤 작업을 모델 자체가 처리할지, 외부 도구(검색, DB, API)로 보낼지를 라우팅 규칙으로 명시합니다. 이것이 없으면 모델이 환각(Hallucination)으로 모든 걸 처리하려 합니다.

---

## Layer 3 — Domain Membrane: HR 도메인 지식의 코드화

이 레이어가 CSP에게 가장 차별화된 레이어입니다. 일반 개발자가 절대 혼자 만들 수 없는 것.

도메인 멤브레인은 두 방향으로 작동합니다. **외부 → 내부 방향**으로는 사용자의 자연어 요청을 모델이 처리할 수 있는 정밀한 태스크로 변환하고, **내부 → 외부 방향**으로는 모델의 출력을 조직 실무자가 바로 사용할 수 있는 언어와 형식으로 번역합니다.

구체적으로는 세 가지 요소로 구성됩니다.

**Ontology Mapping**: ESCON에서 구축하고 있는 Skill Ontology가 바로 이 레이어의 핵심 데이터입니다. "LV3 엔지니어"라는 단어가 들어오면, 이것이 어떤 스킬 노드들과 연결되는지, 어떤 평가 기준으로 판단되는지를 모델에게 주입합니다.

**Organizational Language Glossary**: 각 회사마다 고유한 개념어가 있습니다. LG PRI의 "EXG팀", "AX 내재화", "Physical AI Tech Leader" — 이것들을 모델이 정확히 이해하고 사용하도록 용어집을 하네스에 내장합니다.

**Judgment Heuristics**: 가장 고급 단계입니다. "이 Pulse Check 결과가 개입이 필요한 수준인가?"라는 판단을 모델이 내릴 수 있도록, CSP의 17년 경험에서 나온 휴리스틱을 명시적 규칙으로 코드화합니다. 이것이 "심리학이 코드가 된다"는 것의 실체입니다.

---

## Layer 4 — Output Contract: 결과물의 강제 품질

마지막 레이어는 "잘 나왔는가?"를 시스템이 스스로 판단하게 만드는 구조입니다.

**Schema Enforcement**: 결과물이 반드시 특정 구조를 따르도록 강제합니다. JSON Schema, Pydantic 모델, 혹은 프롬프트 레벨의 XML 태그 — 형태와 관계없이 결과물의 형식을 계약처럼 사전 정의합니다.

**Definition of Done (DoD)**: Ouroboros에서 이미 작업하신 개념입니다. 각 결과물이 "완료"로 인정받으려면 충족해야 하는 조건 목록. "교육 과정 설계서는 학습 목표, 평가 방식, 운영 가이드 세 섹션을 모두 포함해야 한다" — 이런 조건들이 YAML로 선언됩니다.

**Self-Validation Loop**: 모델이 자신의 출력을 DoD 기준으로 스스로 검토하고, 미충족 항목을 재생성하는 루프. 이것이 Ouroboros의 수렴 메커니즘과 정확히 연결됩니다.

---

## 실제 구현 순서 — CSP 맥락에서

추상 개념이 아니라, 지금 당장 어디서부터 시작할지의 문제입니다.

가장 실용적인 순서는 **Layer 4 → Layer 1 → Layer 3 → Layer 2** 역방향입니다. 먼저 원하는 결과물의 계약(Output Contract)을 명확히 정의하고, 그 결과를 낼 수 있는 페르소나(Context Shell)를 설계하고, 도메인 지식(Domain Membrane)을 채우고, 마지막으로 실행 흐름(Workflow Engine)으로 묶는 순서입니다.

왜냐하면 "무엇이 나와야 하는가"가 명확하지 않은 상태에서 레이어를 쌓으면, 결국 아름다운 구조만 있고 실용성 없는 하네스가 됩니다.

지금 ESCON, Pulse Check, 교육 설계 — 이 세 프로젝트 중 어느 것에 먼저 하네스를 씌울지 정하는 것이 다음 질문이 될 것 같습니다. 어떻게 생각하시나요?

## 먼저 진단 — 지금 ESCON의 하네스 공백

현재 ESCON은 Next.js + Supabase 위에서 Skill Ontology 데이터를 저장하고 탐색하는 구조입니다. 기술적으로는 작동하지만, 하네스 관점에서 보면 세 가지 공백이 있습니다.

첫째, **모델이 ESCON의 언어를 모릅니다.** "LV3 엔지니어가 갭 분석을 요청한다"는 맥락을 LLM이 이해하려면, Skill Ontology의 노드 구조와 레벨 정의가 Context Shell에 미리 심어져 있어야 합니다. 지금은 그게 없습니다.

둘째, **사용자의 질문이 Ontology 쿼리로 자동 변환되지 않습니다.** "나 요즘 AI 쪽으로 가고 싶은데 뭘 배워야 해?"라는 자연어가 `skill_node → gap_analysis → learning_path` 순서의 구조화된 쿼리로 변환되는 워크플로우가 없습니다.

셋째, **결과물의 계약이 없습니다.** 갭 분석 결과가 어떤 형식이어야 하는지, 학습 경로 추천이 어떤 조건을 충족해야 "완료"인지 — DoD가 없습니다.

이 세 공백을 4개 레이어로 채우는 것이 ESCON 하네스 엔지니어링의 본질입니다.

## Layer 1 — ESCON Context Shell

```yaml
# escon_context_shell.yaml
persona: |
  당신은 LG PRI의 Engineering Skill Competency Navigator입니다.
  17년 HR 경험과 Production Engineering 도메인 지식을 가진
  전문가의 판단 기준으로 작동합니다.

  핵심 판단 기준:
  - 스킬 레벨은 LV1(인지) → LV2(적용) → LV3(설계) → LV4(혁신)으로 정의됩니다
  - 갭 분석은 현재 수준과 목표 역할의 요구 수준 차이를 정량화합니다
  - 학습 경로 추천은 항상 실행 가능성(6개월 이내 달성 가능)을 기준으로 합니다

domain_glossary:
  "Physical AI Tech Leader": "물리 AI를 설계·운영할 수 있는 LV3 이상 엔지니어"
  "AX 내재화": "AI 도구를 일상 업무 워크플로우에 통합한 상태"
  "Skill Ontology": "직무별 필요 역량을 노드-엣지 구조로 표현한 지식 그래프"

constraints:
  - 스킬 추천은 반드시 Ontology에 존재하는 노드만 사용
  - 레벨 평가는 증거 기반(보유 자격증, 프로젝트 경험)으로만 수행
  - 불확실한 경우 추정이 아닌 추가 질문으로 대응
```

이것이 Layer 1의 실체입니다. 단순한 역할 부여가 아니라, **판단 기준 + 도메인 용어 + 행동 제약**의 3중 구조.

---

## Layer 2 — Workflow Engine: 세 가지 핵심 플로우

ESCON에서 발생하는 사용자 인터랙션을 세 가지 워크플로우로 정의합니다.

```
This block is not supported on your current device yet.
```

세 가지 워크플로우의 핵심은 **Intent Router**입니다. "나 Python 배우고 싶어"와 "내가 LV3 되려면 뭐가 부족해?"는 전혀 다른 플로우로 라우팅되어야 합니다. 이 분류 자체를 LLM이 담당하게 하는 것 — 이것이 하네스의 첫 번째 지능입니다.

각 플로우 내부는 **CoT(Chain-of-Thought) 단계 강제**로 구성됩니다. 갭 분석 플로우를 예시로 들면:

```
Step 1. 현재 역할과 목표 역할을 명확히 파악 (질문 생성)
Step 2. 각 역할의 필요 스킬 노드를 Ontology에서 조회
Step 3. 보유 스킬과 필요 스킬의 교집합/차집합 계산
Step 4. 갭의 우선순위를 비즈니스 임팩트 기준으로 정렬
Step 5. Output Contract 형식으로 결과 반환
```

각 Step은 독립적으로 실행되고 검증됩니다. Step 2에서 Ontology 조회 결과가 없으면 Step 3으로 넘어가지 않고, 사용자에게 스킬 정의를 요청합니다.

---

## Layer 3 — ESCON Domain Membrane: 온톨로지를 모델 언어로

이 레이어가 ESCON 하네스의 가장 독창적인 부분입니다. Skill Ontology의 구조적 데이터를 LLM이 추론에 사용할 수 있는 형태로 실시간 변환합니다.

구체적으로는 세 가지 변환이 일어납니다.

**Dynamic Context Injection**: 사용자가 특정 스킬 노드에 대해 질문하면, 해당 노드와 연결된 상위/하위/관련 노드들을 Supabase에서 조회해서 즉시 프롬프트에 주입합니다. 정적인 문서가 아니라 질문에 따라 동적으로 달라지는 컨텍스트입니다.

```typescript
// domain_membrane.ts
async function injectSkillContext(userQuery: string, db: SupabaseClient) {
  // 1. 쿼리에서 스킬 엔티티 추출 (LLM 호출)
  const entities = await extractSkillEntities(userQuery);

  // 2. Ontology에서 관련 노드 조회
  const skillNodes = await db
    .from("skill_nodes")
    .select("*, skill_edges(*)")
    .in("name", entities);

  // 3. 컨텍스트 문자열로 변환
  return formatOntologyContext(skillNodes);
  // → "Python(LV1-4): 데이터 처리, ML 파이프라인, API 개발에 필요.
  //    상위 노드: Software Engineering
  //    연결 스킬: SQL(필수), Docker(권장), FastAPI(선택)"
}
```

**Level Translation**: LV1~4라는 숫자를 LLM이 의미적으로 이해하도록 번역합니다. 단순히 "LV3 = 설계 가능"이 아니라, "LV3는 동료에게 가르칠 수 있고, 새로운 상황에 응용할 수 있으며, 표준을 만들 수 있는 수준"으로 풀어서 주입합니다.

**Gap Heuristics**: CSP의 HR 판단력을 규칙으로 코드화한 부분입니다. 예를 들어 "갭이 2레벨 이상이면 직접 학습보다 멘토링 추천", "6개월 내 달성 불가능한 갭은 단계적 로드맵으로 분리", "현재 프로젝트와 연결되지 않는 스킬은 우선순위 하향" — 이런 휴리스틱들이 Domain Membrane에 내장됩니다.

## Layer 4 — Output Contract: ESCON 결과물의 DoD

```yaml
# escon_output_contract.yaml

gap_analysis_contract:
  required_fields:
    - current_level: integer (1-4)
    - target_level: integer (1-4)
    - gap_score: float (0.0-1.0)
    - priority_skills: array (max 3)
    - timeline_estimate: string ("3개월" | "6개월" | "12개월+")

  validation_rules:
    - gap_score > 0.7 → escalate_to_mentoring: true
    - timeline_estimate == "12개월+" → split_into_phases: true
    - priority_skills.length == 0 → status: "no_gap_found"

  dod_checklist:
    - [ ] 현재 레벨 근거 명시 (증거 기반)
    - [ ] 목표 역할 Ontology 노드와 매핑 완료
    - [ ] 우선순위 스킬 3개 이하로 집중
    - [ ] 타임라인이 실행 가능한 범위인지 검증

learning_path_contract:
  required_fields:
    - phases: array of phase objects
    - each_phase:
        - duration: string
        - skills: array
        - milestone: string (측정 가능한 성취 기준)
        - resources: array (최소 1개)

  dod_checklist:
    - [ ] 각 Phase의 마일스톤이 측정 가능한가
    - [ ] 리소스가 실제 접근 가능한가 (내부/외부 구분)
    - [ ] 전체 기간이 12개월 이내인가
```

이 계약이 있으면 LLM이 "어느 정도 나왔으면 됐겠지"하고 멈추는 것을 막습니다. DoD 체크리스트 미충족 항목이 있으면 자동으로 재생성 루프에 들어갑니다.

## Skyhive Skill Ontology의 수준

Skyhive(현 SAP Workforce Intelligence)의 Skill Ontology는 대략 이런 구조입니다.

전 세계 ~25만 개 이상의 스킬 노드, ESCO/O\*NET 같은 표준 분류체계와 매핑, 직무-스킬-학습경로 3중 그래프 구조, 실시간 노동시장 데이터와 연동되는 temporal validity, 그리고 스킬 간 유사도(semantic similarity)를 벡터 공간에서 계산하는 임베딩 레이어까지 갖춘 시스템입니다.

이것을 ESCON의 Output Contract 기준으로 삼으면 어떻게 될까요?

---

## 솔직한 진단: 두 가지 차원을 분리해야 합니다

**데이터 범위** 측면에서는 — 오버스펙입니다. Skyhive는 전사 범용 시스템이고, ESCON은 LG PRI Production Engineering 도메인에 특화된 시스템입니다. 25만 개 스킬 노드가 아니라 수백~수천 개의 도메인 특화 노드로 충분합니다. 노동시장 실시간 연동도 현재 단계에서는 불필요합니다.

**구조적 정교함** 측면에서는 — 오버스펙이 아닙니다. 오히려 참고해야 할 부분이 있습니다. Skyhive가 잘하는 것들 중 ESCON에 반드시 필요한 것들이 있거든요.

## ESCON Output Contract에 실제로 필요한 수준

CSP의 맥락에서 적정 스펙을 세 단계로 나눠보겠습니다.

**지금 당장 필요한 것 (v1 — Week 1 목표):**

```yaml
gap_analysis_output:
  skill_node:
    id: string
    name: string
    current_level: 0-4 # 0=미보유
    required_level: 1-4
    gap: integer # required - current
    evidence: string # 보유 근거 (자격증, 프로젝트명)

  priority_ranking:
    basis: "business_impact | learning_efficiency | urgency"
    top_3: array[skill_node]

  timeline:
    estimate: "3mo | 6mo | 12mo+"
    confidence: "high | medium | low"
```

이 정도면 실제로 엔지니어와 대화하면서 갭을 짚어낼 수 있습니다.

**Skyhive에서 빌려올 가치가 있는 것 (v2 — 이후 단계):**

노드 간 관계의 방향성입니다. Skyhive는 스킬을 단순 목록이 아니라 **선행-후행 관계(prerequisite graph)**로 설계합니다. "Docker를 모르면 Kubernetes를 배울 수 없다"는 구조. ESCON에서도 이게 있어야 학습 경로 추천이 의미있어집니다.

또 하나는 **프로피시언시 디스크립터(Proficiency Descriptor)**입니다. "LV3 = 설계 가능"이 아니라, 각 스킬의 레벨별로 "이 사람이 실제로 무엇을 할 수 있는가"를 행동 동사로 기술하는 것. Skyhive 방식으로는 너무 무겁지만, LG PRI 도메인에서 핵심 스킬 30~50개에 대해서는 충분히 만들 수 있습니다.

**굳이 안 해도 되는 것 (Skyhive 따라하지 말 것):**

시맨틱 임베딩 기반 스킬 유사도 계산, 노동시장 데이터 연동, 범용 분류체계(ESCO) 전체 매핑 — 이것들은 ESCON의 목표인 "LG PRI 엔지니어의 성장 경로 설계"와 직접 연관이 없습니다. 지금 단계에서 이걸 넣으면 인프라 복잡도만 올라가고 실제 사용자 가치는 나오지 않습니다.

## 결론: 적정 스펙의 기준

Skyhive를 참조 모델로 삼되, **구조적 철학은 빌리고 데이터 범위는 대폭 축소**하는 것이 맞습니다.

구체적으로 ESCON v1 Output Contract의 목표 수준은 이렇게 설정하면 됩니다. "LG PRI의 Production Engineering 직군 핵심 스킬 100개에 대해, 선행-후행 관계와 레벨별 행동 기술자를 갖추고, 갭 분석 결과를 JSON으로 반환하는 계약." 이 범위면 Skyhive의 구조적 정교함을 95% 따라가면서 구현 복잡도는 10% 수준으로 유지할 수 있습니다.

지금 Output Contract 초안을 실제로 작성해볼까요? 핵심 스킬 도메인을 먼저 같이 정의하면 됩니다 — Production Engineering에서 가장 중요한 스킬 클러스터가 어떻게 구성되는지 CSP가 가장 잘 아실 테니까요.

## DoD와 Output Contract의 관계 — 한 문장 정리

Contract는 **설계도**, DoD는 **시공 검사 기준**입니다. 집을 지을 때 설계도대로 지었는지 확인하는 체크리스트가 DoD입니다. Contract 없이 DoD를 만들면 검사 기준이 없고, DoD 없이 Contract만 있으면 결과물이 기준에 맞는지 아무도 모릅니다.

그리고 `auto_validatable: false` 항목들 — GA-02, SD-01 — 이것들이 흥미롭습니다. 이 항목들은 코드로 검증할 수 없고, **LLM이 자기 자신의 출력을 판단**해야 합니다. 이게 바로 Self-Validation Loop의 핵심이고, Ouroboros의 수렴 메커니즘과 연결되는 지점입니다.

## Step 3 — ContractValidator.ts (런타임 검증 엔진)

이게 DoD를 실제로 실행하는 코드입니다. `auto_validatable: true` 항목은 여기서 처리합니다.

```typescript
// lib/validator/ContractValidator.ts
import Ajv from "ajv";
import addFormats from "ajv-formats";
import gapSchema from "../../contracts/schemas/gap_analysis.schema.json";

const ajv = new Ajv({ allErrors: true });
addFormats(ajv);

export type ValidationResult = {
  passed: boolean;
  errors: DoDError[];
  warnings: string[];
  requiresJudge: string[]; // auto_validatable: false 항목 ID
};

export type DoDError = {
  id: string;
  message: string;
  autoFixed?: boolean;
};

export class ContractValidator {
  validateGapAnalysis(data: unknown): ValidationResult {
    const errors: DoDError[] = [];
    const requiresJudge: string[] = [];

    // C-01 ~ C-04: JSON Schema 검증 (자동)
    const validate = ajv.compile(gapSchema);
    if (!validate(data)) {
      validate.errors?.forEach((e) => {
        errors.push({ id: "C-01", message: e.message ?? "Schema violation" });
      });
      return { passed: false, errors, warnings: [], requiresJudge };
    }

    const d = data as any;

    // GA-01: self_assessment 단독 시 confidence는 'low'여야
    d.skill_gaps.forEach((gap: any) => {
      if (
        gap.evidence?.source === "self_assessment" &&
        gap.learning_feasibility.confidence !== "low"
      ) {
        errors.push({
          id: "GA-01",
          message: `${gap.skill_id}: self_assessment 근거인데 confidence가 low가 아닙니다.`,
        });
      }
    });

    // GA-03: missing_prerequisites가 top_3에 포함되면 안 됨
    const missingSet = new Set(d.escalation_flags.missing_prerequisites);
    d.priority_ranking.top_3.forEach((skillId: string) => {
      if (missingSet.has(skillId)) {
        errors.push({
          id: "GA-03",
          message: `${skillId}: 선행 스킬 미충족인데 top_3에 포함되어 있습니다.`,
        });
      }
    });

    // GA-04: overall_readiness 수학적 일관성
    const avgGap =
      d.skill_gaps.reduce((sum: number, g: any) => sum + g.gap, 0) /
      (d.skill_gaps.length || 1);
    const expectedReadiness = Math.max(0, 1 - avgGap / 4);
    if (Math.abs(d.summary.overall_readiness - expectedReadiness) > 0.15) {
      errors.push({
        id: "GA-04",
        message: `overall_readiness(${d.summary.overall_readiness}) 값이 gap 데이터와 불일치합니다.`,
      });
    }

    // GA-02: rationale 품질 → LLM judge 필요
    requiresJudge.push("GA-02");

    return {
      passed: errors.length === 0,
      errors,
      warnings: [],
      requiresJudge,
    };
  }
}
```

## Step 4 — DoDJudge.ts (`auto_validatable: false` 처리)

// lib/validator/DoDJudge.ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

export class DoDJudge {
  async judgeRationale(rationale: string): Promise<{
    passed: boolean;
    reason: string;
  }> {
    const response = await client.messages.create({
      model: "claude-sonnet-4-6",
      max_tokens: 200,
      messages: [
        {
          role: "user",
          content: `다음 우선순위 선정 rationale이 비즈니스 임팩트와 실행 가능성을 
근거로 하는지 판단하라. JSON으로만 응답: {"passed": true/false, "reason": "한 줄 이유"}

Rationale: "${rationale}"`,
        },
      ],
    });

    const text =
      response.content[0].type === "text" ? response.content[0].text : "";
    return JSON.parse(text);
  }

  async judgeDescriptors(descriptors: Record<string, string>): Promise<{
    passed: boolean;
    failed_levels: string[];
  }> {

      max_tokens: 200,
      messages: [

JSON으로만 응답: {"passed": true/false, "failed_levels": ["lv1", ...]}

Descriptors: ${JSON.stringify(descriptors)}`,
        },
      ],
    });

    const text =
      response.content[0].type === "text" ? response.content[0].text : "";

## Step 6 — API 라우트에 검증 연결

```typescript
// app/api/gap-analysis/route.ts (Next.js App Router)
import { ContractValidator } from "@/lib/validator/ContractValidator";
import { DoDJudge } from "@/lib/validator/DoDJudge";

const validator = new ContractValidator();
const judge = new DoDJudge();

export async function POST(req: Request) {
  const { userId, targetRole } = await req.json();

  let result = null;
  let attempts = 0;
  const MAX_RETRY = 3;

  while (attempts < MAX_RETRY) {
    // 1. LLM으로 Gap Analysis 생성
    result = await generateGapAnalysis(userId, targetRole);

    // 2. Contract 자동 검증
    const validation = validator.validateGapAnalysis(result);

    if (!validation.passed) {
      attempts++;
      continue; // 재생성
    }

    // 3. LLM Judge 검증 (rationale 품질)
    const judgeResult = await judge.judgeRationale(
      result.priority_ranking.rationale,
    );

    if (!judgeResult.passed) {
      attempts++;
      continue;
    }

    // 4. 모두 통과 → 반환
    return Response.json({ success: true, data: result });
  }

  // max retry 초과
  return Response.json(
    {
      success: false,
      data: result,
      flag: "partial_result_with_human_review_flag",
    },
    { status: 206 },
  );
}
```

## 전체 흐름 요약

지금까지 설계한 것들이 실제 코드 레벨에서 어떻게 연결되는지 한 줄로 정리하면 이렇습니다.

```
사용자 요청
  → Intent Router (어떤 Contract인지 판단)
  → LLM 응답 생성 (Domain Membrane 컨텍스트 포함)
  → ContractValidator.validate() [C-01~C-04, GA-01~GA-04 자동 검증]
  → DoDJudge.judge() [GA-02 LLM judge]
  → 통과 시 반환 / 실패 시 재생성 (max 3회)
  → max retry 초과 시 human_review_flag
```

### 트러블슈팅 — 자주 발생하는 문제

Claude Code 세션에서 막히는 지점별 대응입니다.

**ajv import 에러 발생 시:**

```
ajv를 ESM 방식으로 import하면 에러가 날 수 있어.
import Ajv from 'ajv' 대신
const Ajv = require('ajv'); const ajv = new Ajv();
방식으로 바꿔줘.
```

**tsconfig 경로 에러 시:**

```
tsconfig.json에서 paths 설정 확인하고
@/ 앨리어스가 없으면 상대경로로 import 수정해줘.
```

**Jest + TypeScript 설정 에러 시:**

```
jest.config.ts를 열고
preset: 'ts-jest' 설정이 있는지 확인하고
없으면 추가해줘.
```
