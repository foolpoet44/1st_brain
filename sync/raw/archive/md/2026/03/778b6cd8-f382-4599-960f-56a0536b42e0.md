---

**워크플로우 다이어그램**은 Git의 전체 여정을 4개의 레이어로 구성했습니다. 로컬 작업(수정 → 스테이징 → 커밋), 브랜치 전략(main / develop / feature / release / hotfix), 원격 협업(push → PR → merge), CI/CD 배포 파이프라인 순서입니다. 각 박스를 클릭하면 해당 개념에 대한 심층 질문이 자동으로 이어집니다.

**명령어 레퍼런스 카드**는 탭으로 구분해서 시작, 브랜치, 원격, 되돌리기, 심화 명령어를 카테고리별로 볼 수 있게 했습니다.

---

HR 시스템 관점에서 비유하자면, Git의 구조는 조직의 의사결정 흐름과 놀랍도록 닮아 있습니다. `main`은 공식 기록된 인사 결정, `feature` 브랜치는 TF에서 검토 중인 안건, `Pull Request`는 검토 위원회, `merge`는 최종 승인 후 시스템 반영입니다. 실수를 되돌리는 `revert`와 `reset`의 차이도 마찬가지인데, revert는 "취소 공문을 새로 발행하는 것"이고 reset은 "그 결정 자체가 없었던 것으로 만드는 것"입니다. 협업 중에는 반드시 revert를 쓰는 이유가 바로 여기에 있습니다.

---

9가지 실수를 관통하는 공통 철학이 있습니다. Git의 모든 실수는 사실 두 가지 인지 오류에서 비롯됩니다.

첫 번째는 "되돌릴 수 없다는 착각"입니다. `reset --hard`로 날린 커밋도 `reflog`로 복구할 수 있고, 잘못 push된 커밋도 대부분 흔적을 지울 수 있습니다. 겁먹지 말고 침착하게 `git reflog`를 먼저 실행하는 것이 사고 대응의 첫 번째 반사 행동이 되어야 합니다.

두 번째는 "나만 쓰는 코드라는 착각"입니다. 혼자 작업하는 것처럼 느껴지더라도 Git 히스토리는 미래의 자신과 팀원에게 보내는 편지입니다. `--force-with-lease`를 쓰고, 커밋 메시지를 성의 있게 쓰고, 브랜치 이름에 의도를 담는 행위는 모두 같은 뿌리에서 나옵니다. 협업은 공간을 공유하는 것이 아니라 히스토리를 공유하는 것이라는 감각, 그것이 Git 숙련도의 본질입니다.

위 가이드는 브랜치의 전체 생명주기 — 생성 → 작업 → 머지 → 정리 — 를 6단계 탭으로 정리했습니다. 특히 마지막 두 탭(전략, 팀 규칙)은 팀 도입 시 의사결정 기준으로 쓸 수 있습니다.

---

브랜치 관리의 본질을 심리학적으로 해석하면 흥미롭습니다. 브랜치는 사실 인간의 인지 구조를 코드로 모방한 것입니다. 우리가 "이 방향으로 가면 어떨까?" 라고 머릿속에서 시뮬레이션을 돌리는 것처럼, Git은 코드베이스 전체를 복제하지 않고도 "만약에(what-if)" 실험을 가능하게 합니다.

그래서 좋은 브랜치 습관의 핵심은 두 가지입니다.

첫 번째는 의도의 명시화입니다. `feature/EX-123-login-jwt-refresh`라는 브랜치 이름은 단순한 명명 규칙이 아니라, 이 코드 변화가 왜 존재하는지를 히스토리에 영구적으로 각인하는 행위입니다. 6개월 뒤 `git log --oneline`을 봤을 때 타임라인이 소설처럼 읽혀야 합니다.

두 번째는 분리와 통합의 리듬입니다. 너무 오래 분리하면 머지할 때 충돌 폭탄이 되고, 너무 자주 통합하면 브랜치의 의미가 없어집니다. 하루 1회 base 브랜치 fetch, PR 단위는 하나의 의미 있는 기능 — 이 리듬이 팀 전체의 심리적 안전감을 만들어냅니다. 코드 리뷰가 무겁지 않고, 배포가 두렵지 않은 팀은 대부분 이 리듬을 잘 지키고 있습니다.

## Human (Message 7)

develop feature hotfix 브랜치는 별도로 설정하지 않아도 자동으로 리포에서 생성되는 개념인가?

## Claude (Message 8)

아니요, 자동 생성되지 않습니다. 모두 직접 만들어야 합니다.

이 개념이 처음에 헷갈리는 이유가 있습니다. `main`(또는 `master`)은 GitHub에서 리포지토리를 생성할 때 자동으로 만들어주지만, `develop`, `feature/*`, `hotfix/*`는 Git Flow라는 협업 전략(convention)이지 Git 자체의 기능이 아닙니다. Git 입장에서는 이름이 `develop`이든 `banana`이든 동등한 브랜치입니다. 의미를 부여하는 것은 팀의 약속이지, 도구의 규칙이 아닙니다.

```

```

Git Flow를 처음 셋업할 때 실행하는 순서는 이렇습니다.

```bash
# 리포 생성 직후 — main만 존재하는 상태

# 1. develop 브랜치 생성 (팀 공유용 통합 브랜치)
git checkout -b develop main
git push origin develop

# 2. 작업 시작할 때마다 feature 브랜치 생성
git checkout -b feature/user-auth develop

# 3. 긴급 이슈 발생 시 hotfix 브랜치 생성
git checkout -b hotfix/login-crash main

# 4. 배포 준비 시 release 브랜치 생성
git checkout -b release/v1.0 develop
```

`git-flow`라는 CLI 툴을 쓰면 이 과정을 자동화할 수도 있습니다. `git flow init`을 실행하면 develop 브랜치 생성과 브랜치 네이밍 컨벤션 설정을 대화형으로 안내해줍니다. 하지만 이것 역시 별도 설치가 필요한 외부 도구이지, Git에 내장된 기능이 아닙니다.

정리하면, Git이 자동으로 해주는 것은 `main` 하나뿐이고, 나머지는 모두 팀이 선택하고 직접 만드는 것입니다. Git Flow는 "이렇게 브랜치를 쓰면 협업이 잘 된다"는 업계의 집단 지혜가 굳어진 패턴이지, Git 자체에 하드코딩된 규칙이 아닙니다.
