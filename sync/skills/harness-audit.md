# 스킬: Harness Audit (하네스 진단)

> csp-brain 의 Harness Engineering 건강도를 진단합니다.

---

## 언제 쓰는가

- 월 1 회 정기 진단
- 새로운 스킬/프로토콜 추가 후
- 조직 확장 전 (Green Field → Brown Field 전환점)
- "뭔가 비효율적인데"라는 느낌이 들 때

---

## 진단 항목

### 1. 구조 설계 (Structure)

```
체크리스트:
[ ] CLAUDE.md 가 현재 상태를 반영하는가?
[ ] .claude/rules/ 파일들이 중복 없이 분리되는가?
[ ] skills/ 폴더가 실제 사용되는가? (사용 로그 확인)
[ ] 폴더 구조가 일관된 규칙을 따르는가?
```

**점수:** 0-4 점 (각 항목 1 점)

---

### 2. 맥락 관리 (Context)

```
체크리스트:
[ ] wiki/ 문서당 평균 백링크 2 개 이상인가?
[ ] inbox/ 처리율 (처리됨/전체) 이 50% 이상인가?
[ ] projects/ Compiled Truth 가 현재 상태를 반영하는가?
[ ] 고립 문서 (백링크 0 개) 가 없는가?
```

**점수:** 0-4 점 (각 항목 1 점)

---

### 3. 실행 흐름 (Workflow)

```
체크리스트:
[ ] Dream Cycle 이 주간으로 실행되는가?
[ ] INGEST 프로토콜이 inbox 적체 시 실행되는가?
[ ] Git 커밋이 의미 있는 단위로 분리되는가?
[ ] 커밋 메시지가 "무엇을"보다 "왜"를 설명하는가?
```

**점수:** 0-4 점 (각 항목 1 점)

---

### 4. 검증 기준 (Validation)

```
체크리스트:
[ ] LINT 프로토콜이 체크리스트를 가지는가?
[ ] frontmatter 필수 필드가 완성되는가?
[ ] 스킬 문서가 실제 동작하는가?
[ ] 6 주 이상 미갱신 Compiled Truth 가 없는가?
```

**점수:** 0-4 점 (각 항목 1 점)

---

### 5. 반복 개선 (Iteration)

```
체크리스트:
[ ] 주간 다이제스트가 생성되는가?
[ ] 분석 리포트 (analysis/) 가 축적되는가?
[ ] 이전 진단 대비 개선 항목이 있는가?
[ ] Git 히스토리가 학습 증거를 보존하는가?
```

**점수:** 0-4 점 (각 항목 1 점)

---

## 실행 단계

### 1. 자동 수집

```bash
# Git 로그에서 커밋 패턴 분석
git log --oneline --since="4 weeks ago"

# 백링크 밀도 계산
grep -r "\[\[.*\]\]" wiki/ | wc -l
wiki 문서 수로 나누기

# inbox 처리율 계산
inbox/ 파일 수 vs processed 항목 수
```

### 2. 수동 점검

- CLAUDE.md 최종 수정일 확인
- skills/ 폴더 실제 사용 여부 (기억 더듬기)
- projects/ README.md 갱신 상태

### 3. 점수화 및 리포트

**총점:** \_\_\_ / 20 점

| 등급  | 점수  | 의미                |
| :---- | :---- | :------------------ |
| **S** | 18-20 | 조직 확장 준비 완료 |
| **A** | 15-17 | 안정적 운영 중      |
| **B** | 12-14 | 개선 필요 항목 존재 |
| **C** | 9-11  | 구조 재설계 권고    |
| **D** | 0-8   | 초기 구축 단계      |

## 관련 스킬

- `lint` — 위키 문서 수준 점검
- `dream-cycle` — 주간 정리 루틴
- `generate-linkedin` — 진단 결과 공유용 포스트 생성

---

## 메모

- Harness Engineering 은 "개인 생산성"이 아니라 "조직 재현성"이 핵심
- Green Field(현재) 에서는 가벼운 구조로 충분하나, Brown Field 전환 대비 필요
- 점수보다 "추세" (상승/하락) 가 더 중요
