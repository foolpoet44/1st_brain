# 2026-05-01

**MS Copilot 친화적인 데이터 매니지먼트**란 한마디로,  
**Copilot이 “찾을 수 있고, 믿을 수 있고, 써도 되는 데이터”만 안전하게 활용하도록 조직의 지식 환경을 정리하는 것**입니다.

Microsoft 365 Copilot은 Microsoft Graph, SharePoint, OneDrive, Outlook, Teams, 회의, 문서 등 사용자가 권한을 가진 업무 데이터를 기반으로 답변합니다. Microsoft 문서에서도 Copilot과 Agent는 기존 권한, 공유 설정, 정책을 존중하고, Microsoft Graph 및 Graph 커넥터 데이터를 사용자의 접근 권한 범위 안에서 활용한다고 설명합니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-privacy?utm_source=chatgpt.com "Data, Privacy, and Security for Microsoft 365 Copilot"))

---

# 1. 핵심 개념: Copilot은 “권한 있는 쓰레기 데이터”도 똑똑하게 읽는다

Copilot 도입에서 가장 위험한 착각은 이것입니다.

> “보안 권한이 있으니 괜찮겠지.”

하지만 실제 문제는 다릅니다.

Copilot은 사용자가 접근 가능한 데이터를 바탕으로 답합니다. 그래서 예전에는 사람이 굳이 찾지 못했던 문서도, Copilot은 빠르게 찾아 요약할 수 있습니다. 즉, **권한이 과도하게 열려 있거나, 오래된 문서가 방치되어 있거나, 민감자료가 일반 폴더에 섞여 있으면 Copilot이 그 문제를 증폭시킬 수 있습니다.**

그래서 Copilot 친화적인 데이터 매니지먼트의 첫 원칙은 다음입니다.

> **“AI에게 더 많이 보여주는 것”이 아니라, “AI가 봐도 되는 것을 정확히 정리하는 것.”**

---

# 2. Copilot 친화 데이터의 5가지 조건

## ① 접근권한이 정확해야 한다

Copilot은 기존 Microsoft 365 권한과 공유 설정을 존중합니다. 그래서 SharePoint, OneDrive, Teams의 권한 구조가 곧 Copilot의 지식 접근 경계가 됩니다. Microsoft도 Copilot과 Agent를 준비하려면 콘텐츠가 최신 상태이고 잘 거버넌스되어야 하며, SharePoint Advanced Management를 통해 과도한 공유를 줄이라고 안내합니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/get-ready-copilot-sharepoint-advanced-management?utm_source=chatgpt.com "Get ready for Microsoft 365 Copilot with SharePoint Advanced ..."))

**정리해야 할 것**

| 점검 항목                     | 위험                                     |
| ----------------------------- | ---------------------------------------- |
| Everyone / 전사 공유 문서     | 민감 정보가 Copilot 응답에 포함될 가능성 |
| Anyone with link              | 외부 유출 및 과도한 접근                 |
| 퇴사자·전보자 권한            | 과거 권한이 계속 유지                    |
| 오래된 TF/프로젝트 Teams      | 종료된 과제 자료가 계속 노출             |
| 소유자 없는 SharePoint 사이트 | 책임 없는 데이터 방치                    |

Copilot 친화 데이터 관리는 결국 **권한 다이어트**에서 시작합니다.

---

## ② 민감도가 분류되어 있어야 한다

Microsoft Purview의 민감도 레이블은 조직 데이터를 분류하고 보호하기 위한 핵심 기능입니다. Microsoft는 민감도 레이블이 데이터 분류와 보호를 지원하면서도 협업 생산성을 방해하지 않도록 설계되었다고 설명합니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/purview/sensitivity-labels?utm_source=chatgpt.com "Learn about sensitivity labels"))

Copilot 시대에는 민감도 레이블이 단순한 보안 태그가 아닙니다.  
**Copilot이 이 데이터를 요약·참조·응답에 활용해도 되는지 판단하는 통제 신호**가 됩니다.

추천 레이블 구조는 단순해야 합니다.

| 레이블            | 의미             | 예시                           |
| ----------------- | ---------------- | ------------------------------ |
| Public            | 외부 공개 가능   | 채용 브로슈어, 공개 보도자료   |
| Internal          | 일반 사내 정보   | 일반 공지, 업무 매뉴얼         |
| Confidential      | 제한된 내부 정보 | 전략, 예산, 프로젝트 계획      |
| HR Confidential   | HR 민감 정보     | 평가, 보상, 인사이동, 조직진단 |
| Highly Restricted | 극소수 접근      | 징계, 노무, M&A, 임원 인사     |

특히 HR 조직은 **HR Confidential**을 별도로 두는 것이 좋습니다. 평가, 보상, 고충, 노무, 조직개편 문서는 일반 업무 문서와 같은 규칙으로 관리하면 안 됩니다.

---

## ③ 최신성과 상태값이 있어야 한다

Copilot이 틀리는 대표적인 이유는 “오래된 문서를 최신 기준처럼 읽는 것”입니다.

예를 들어 다음 문서들이 같이 존재한다고 해보겠습니다.

```text
DX_Enabler_평가기준_2024.pptx
DX_Enabler_평가기준_2025_수정.pptx
DX_Enabler_최종안_진짜최종.pptx
AX전환_연계_2026_DXEnabler_평가기준_v1.0.docx
```

사람도 헷갈리는데 Copilot도 헷갈립니다.

그래서 주요 문서에는 반드시 상태값이 필요합니다.

| 상태값     | 의미      |
| ---------- | --------- |
| Draft      | 작성 중   |
| Review     | 검토 중   |
| Approved   | 승인 완료 |
| Active     | 현재 기준 |
| Deprecated | 폐기됨    |
| Archived   | 보관용    |

문서 상단에는 이런 메타데이터를 넣는 것이 좋습니다.

```markdown
Status: Active
Owner: HRD팀
Last Updated: 2026-05-01
Applies To: 2026년 AX 전환 교육 운영
Replaces: 2025년 DX Enabler 운영안
Confidentiality: Internal
```

이런 정보가 있어야 Copilot이 “무엇이 현재 기준인지” 더 잘 판단할 수 있습니다.

---

## ④ 문서가 구조화되어 있어야 한다

Copilot은 비정형 문서도 읽지만, 구조화된 문서를 훨씬 잘 이해합니다.

좋은 Copilot 친화 문서는 이런 구조를 가집니다.

```markdown
# 문서 제목

## 1. 목적

이 문서가 필요한 이유

## 2. 적용 범위

대상 조직, 대상자, 적용 기간

## 3. 핵심 기준

정책, 원칙, 판단 기준

## 4. 절차

단계별 수행 방식

## 5. 예외 처리

예외 상황과 승인 기준

## 6. 담당자

Owner, Reviewer, Approver

## 7. 관련 문서

연결된 정책, 템플릿, 회의록
```

Copilot 친화적이지 않은 문서는 이런 형태입니다.

```text
대표님보고_수정본_진짜최종_최종2.pptx
```

Copilot 친화적인 문서는 이런 형태입니다.

```text
2026_HRD_AX전환교육_운영기준_v1.0_Active.docx
```

이름만 바꿔도 Copilot의 검색·요약 품질이 올라갑니다.

---

## ⑤ 출처의 신뢰도가 정해져 있어야 한다

Copilot이 여러 데이터를 읽을 수 있게 되면, 반드시 이런 문제가 생깁니다.

> “조직도는 HRIS가 맞는가, Teams 멤버 목록이 맞는가?”  
> “교육 수료 여부는 LMS가 맞는가, 엑셀 취합본이 맞는가?”  
> “직무 정보는 인사 시스템이 맞는가, 팀장이 만든 PPT가 맞는가?”

그래서 Copilot 친화 데이터 매니지먼트에는 **Source of Truth**가 필요합니다.

| 질문              | 기준 데이터                           |
| ----------------- | ------------------------------------- |
| 구성원의 소속은?  | HRIS                                  |
| 교육 수료 여부는? | LMS                                   |
| 공식 정책은?      | SharePoint 공식 정책 저장소           |
| 프로젝트 상태는?  | Planner, Jira, Monday 등 공식 PM 도구 |
| 회의 결정사항은?  | Teams 회의록 + 승인된 Action Log      |
| 조직 건강도는?    | 비식별·집계된 Pulse Check 데이터      |
| 직무/역량 기준은? | Skill Ontology DB                     |

Copilot이 여러 문서를 섞어 답할수록, “어떤 데이터가 기준인지”가 중요해집니다.

# 3. Copilot 친화 데이터 매니지먼트 운영 모델

저라면 다음 6단계로 설계합니다.

## 1단계. 데이터 지도 만들기

먼저 조직의 데이터가 어디에 있는지 파악합니다.

| 데이터 영역    | 위치           | 소유자   | 민감도          | Copilot 활용 여부 |
| -------------- | -------------- | -------- | --------------- | ----------------- |
| HR 정책        | SharePoint     | HR기획   | Confidential    | 제한 활용         |
| 교육 자료      | SharePoint/LMS | HRD      | Internal        | 활용              |
| 평가 자료      | HRIS/보안폴더  | HRM      | HR Confidential | 원칙적 제한       |
| Pulse 결과     | Survey Tool    | 조직문화 | Confidential    | 집계본만 활용     |
| 회의록         | Teams          | 각 조직  | Internal        | 활용              |
| Skill Ontology | DB/SharePoint  | HRD      | Internal        | 활용              |

이 작업은 거창한 시스템보다 **엑셀 한 장**으로 시작해도 됩니다.

---

## 2단계. 과도한 공유부터 줄이기

Copilot 준비에서 가장 먼저 손댈 것은 “문서 품질”보다 **과도한 공유**입니다.

Microsoft는 SharePoint Advanced Management가 콘텐츠 스프롤, 수명주기, 과도한 공유 방지, 권한 관리를 돕고 Copilot 및 Agent 준비에 유용하다고 설명합니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/sharepoint/advanced-management?utm_source=chatgpt.com "SharePoint Advanced Management overview - Microsoft Learn"))

우선순위는 다음입니다.

```text
Anyone 링크
→ Everyone 공유
→ 외부 공유
→ 소유자 없는 사이트
→ 오래된 프로젝트 사이트
→ 민감정보 포함 폴더
```

---

## 3단계. 민감도 레이블과 DLP 적용

Microsoft Purview는 Microsoft 365 Copilot과 Copilot Chat의 AI 상호작용에 대해 민감도 레이블, 위험 상호작용 탐지, AI 앱 데이터 보안, 감사와 같은 기능을 지원합니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/purview/ai-m365-copilot?utm_source=chatgpt.com "Use Microsoft Purview to manage data security & compliance for ..."))

또한 Microsoft Purview DLP에서는 민감도 레이블이 붙은 파일과 이메일이 Copilot 응답 요약에 포함되지 않도록 제한하는 정책을 만들 수 있습니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/purview/dlp-microsoft365-copilot-location-learn-about?utm_source=chatgpt.com "Learn about using Microsoft Purview Data Loss Prevention ..."))

HR 기준으로는 최소한 아래 정책이 필요합니다.

| 정책                             | 설명                                            |
| -------------------------------- | ----------------------------------------------- |
| HR Confidential 자동/수동 레이블 | 평가, 보상, 인사이동 문서 분류                  |
| Highly Restricted 접근 제한      | 징계, 노무, 임원 인사 자료                      |
| DLP 정책                         | 민감 문서가 Copilot 응답에 활용되지 않도록 제한 |
| 외부 공유 차단                   | HR 민감자료 외부 공유 제한                      |
| 감사 로그                        | Copilot 사용 및 민감자료 접근 추적              |

---

## 4단계. 공식 지식 저장소 만들기

Copilot은 여러 곳의 문서를 찾을 수 있지만, 조직은 **공식 기준 저장소**를 만들어야 합니다.

예를 들어 HR에는 다음과 같은 저장소가 필요합니다.

```text
HR Official Knowledge Base
├─ 01_Policies
├─ 02_Process
├─ 03_FAQ
├─ 04_Templates
├─ 05_Skill Ontology
├─ 06_Pulse Check
├─ 07_AX Education
└─ 99_Archived
```

핵심은 “자료를 모아두는 것”이 아닙니다.  
**Copilot이 답변할 때 기준으로 삼을 정답 문서 세트**를 만드는 것입니다.

---

## 5단계. 문서 라이프사이클 관리

Copilot 친화 데이터는 계속 살아 있어야 합니다.

문서마다 최소한 다음 필드가 필요합니다.

| 필드         | 예시                           |
| ------------ | ------------------------------ |
| Owner        | HRD팀 김OO                     |
| Reviewer     | HR기획팀                       |
| Status       | Active                         |
| Last Updated | 2026-05-01                     |
| Review Cycle | 분기 1회                       |
| Applies To   | 전사 AX 교육                   |
| Sensitivity  | Internal                       |
| Related Docs | Skill Ontology, 교육 운영 기준 |

이렇게 해야 Copilot이 오래된 문서를 기준으로 답하는 문제를 줄일 수 있습니다.

---

## 6단계. 사용 로그와 오답 사례를 관리

Copilot 친화 데이터 매니지먼트는 한 번 정리하고 끝나는 일이 아닙니다.

운영하면서 이런 것을 계속 봐야 합니다.

| 관찰 항목          | 봐야 할 것                      |
| ------------------ | ------------------------------- |
| Copilot 오답       | 어떤 문서를 잘못 참조했는가     |
| 민감정보 노출 위험 | 권한/레이블/DLP 문제인가        |
| 검색 실패          | 문서명/메타데이터/위치 문제인가 |
| 중복 답변          | 기준 문서가 여러 개인가         |
| 오래된 답변        | Archived 문서가 노출되는가      |
| 사용자 불신        | 답변 출처가 불명확한가          |

Microsoft는 Copilot의 데이터 보호 아키텍처에서 Purview 민감도 레이블, 암호화, SharePoint/OneDrive 접근 제어, 감사·컴플라이언스 시나리오를 설명하고 있습니다. ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-365-copilot-architecture-data-protection-auditing?utm_source=chatgpt.com "Microsoft 365 Copilot data protection architecture"))

# 4. HR 조직 기준으로 특히 조심할 데이터

HR은 Copilot 친화 데이터 관리에서 가장 민감한 조직 중 하나입니다.

## Copilot 활용에 적합한 데이터

| 데이터                    | 활용 예                   |
| ------------------------- | ------------------------- |
| 교육과정 안내             | 과정 추천, FAQ            |
| 직무기술서                | 직무별 역량 설명          |
| Skill Ontology            | 역량 매핑, 육성 경로      |
| 일반 HR 정책              | 휴가, 교육, 복리후생 안내 |
| 비식별 Pulse 집계         | 조직 단위 이슈 분석       |
| 공개된 조직 운영 프로세스 | 리더 가이드, 면담 가이드  |

## 제한이 필요한 데이터

| 데이터           | 원칙                          |
| ---------------- | ----------------------------- |
| 개인 평가 코멘트 | Copilot 일반 활용 제한        |
| 보상 상세        | Highly Restricted             |
| 고충/제보        | 원본 비공개, 집계·테마만 활용 |
| 징계/노무        | 극소수 접근                   |
| 건강/심리 정보   | 원칙적 배제 또는 강한 제한    |
| 조직개편 초안    | 제한 접근 + 기간 관리         |

HR에서 중요한 기준은 이것입니다.

> **개인 데이터는 줄이고, 조직 인사이트는 살린다.**

예를 들어 Pulse Check 원본을 Copilot에 직접 연결하기보다, 아래처럼 변환해야 합니다.

```text
개인 응답 원본
→ 비식별화
→ 조직/직군/리더 단위 집계
→ 테마 분류
→ 리스크 수준 산정
→ 권장 액션 플랜
→ Copilot/Agent 활용
```

# 7. CSP님 관점의 최종 정의

CSP님이 추진하는 HR 자동화, Pulse Check, Skill Ontology, AX 전환과 연결하면 이렇게 정의할 수 있습니다.

> **Copilot 친화적인 데이터 매니지먼트란  
> 조직의 문서·회의·사람·스킬·정서 데이터를  
> AI가 안전하게 읽고, 정확하게 해석하고,  
> 실행 가능한 다음 행동으로 바꿀 수 있도록  
> 권한, 의미, 상태, 출처, 민감도를 설계하는 일이다.**

더 짧게 말하면 이것입니다.

> **AI가 읽을 수 있는 데이터가 아니라,  
> AI가 믿고 행동해도 되는 데이터를 만드는 것.**

지금 바로 시작할 최소 단위는 하나입니다.

**HR 문서 저장소를 기준으로 `Active / Deprecated / Confidential / Agent-Readable` 네 가지 태그를 붙이는 것**입니다.  
이 네 가지 태그만 있어도 Copilot 답변 품질과 보안 수준이 동시에 올라갑니다.
