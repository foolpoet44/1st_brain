포스팅 잘 읽었습니다! 실제 경험을 바탕으로 세 개념의 차이를 명쾌하게 정리하셨네요. 이를 바탕으로 좀 더 구조화해서 정리해드릴게요.

## 🎯 핵심 구분 기준

```
실행 타이밍 × 통제 강도 × 적용 범위
```

### **Skill** = 지속적 사고방식

- **언제**: 작업 전체에 걸쳐
- **강도**: 권장 (Claude가 판단 가능)
- **범위**: 특정 도메인/작업 유형

### **Hook** = 특정 시점 강제 실행

- **언제**: 정확한 타이밍 (before/after)
- **강도**: 강제 (시스템이 보장)
- **범위**: 특정 이벤트

### **Agent** = 독립적 역할 분리

- **언제**: 요청 시작부터
- **강도**: 완전 분리 (컨텍스트 독립)
- **범위**: 전체 워크플로우

---

## 📊 의사결정 트리

```
질문 1: "이 작업을 빼먹으면 치명적인가?"
  ├─ YES → Hook 고려
  └─ NO → 질문 2로

질문 2: "다른 역할과 관점을 분리해야 하는가?"
  ├─ YES → Agent 고려
  └─ NO → Skill 사용

추가: "Hook인데 판단이 필요하면?"
  → Hook에서 Agent 호출
```

## 💡 실전 예시 비교

### 예시 1: 코드 품질 관리

**Skill 방식**

```markdown
# Code Quality Standards

- 함수는 20줄 이하
- 변수명은 의미 명확하게
- 주석은 why를 설명
```

→ Claude가 코드 작성하면서 염두에 두고 작성

**Hook 방식**

```markdown
# pre-commit hook

코드 저장 전:

1. Linter 실행
2. 테스트 통과 확인
3. 실패 시 저장 차단
```

→ 시스템이 강제로 검사, 통과 안 하면 다음 단계 불가

**Agent 방식**

```markdown
# Code Reviewer Agent

입력: 작성된 코드
역할: 객관적 리뷰
출력: 개선 제안 + 승인/거부
```

→ 코드 작성자와 분리된 독립적 관점

---

### 예시 2: 문서 작성

**언제 Skill?**

```
"기술 문서는 다음 순서로 작성:
1. 개요
2. 사용법
3. API 레퍼런스
4. 예제"
```

→ 매번 이 순서를 따르되, 상황에 따라 조정 가능

**언제 Hook?**

```
"README.md 수정 시:
- 목차 자동 생성
- 링크 유효성 검증
- 코드 블록 syntax 확인"
```

→ README 저장할 때마다 무조건 실행

**언제 Agent?**

```
Technical Writer Agent:
- 개발자가 작성한 주석을 사용자 친화적 문서로 변환
- 기술 용어를 풀어쓰기
- 예제 코드 추가
```

→ 개발자와 다른 시각으로 문서 재작성

## 🔍 각 방식의 장단점

### Skill

**장점**

- 설정 간단
- 유연한 적용
- 컨텍스트 인식 가능

**단점**

- 누락 가능성
- 대화가 길어지면 약화
- 명시적 강제 불가

**적합한 경우**

- 코딩 스타일 가이드
- 작성 톤앤매너
- 네이밍 컨벤션
- 일반적 작업 방식

### Hook

**장점**

- 100% 실행 보장
- 타이밍 정확
- 실수 방지

**단점**

- 유연성 낮음
- 과하면 느려짐
- 컨텍스트 판단 불가

**적합한 경우**

- 린트/테스트 실행
- 파일 형식 검증
- 필수 체크리스트
- 보안/규정 준수

### Agent

**장점**

- 명확한 역할 분리
- 객관적 관점 확보
- 전문성 집중

**단점**

- 설정 복잡
- 과하면 관리 부담
- 컨텍스트 공유 어려움

**적합한 경우**

- 리뷰어/작성자 분리
- 기획자/개발자 역할
- 연구/적용 단계 구분
- 긴 워크플로우

## 🎨 조합 패턴

### 패턴 1: Skill + Hook

```
Skill: "테스트 커버리지 80% 이상 목표"
Hook: "커밋 전 실제 커버리지 측정, 80% 미만이면 경고"
```

→ 평소엔 의식하고, 마지막엔 강제 검증

### 패턴 2: Agent + Skill

```
Agent: "Backend Developer" (API 구현)
Skill: "RESTful 원칙 준수, OpenAPI 문서 자동 생성"
```

→ 역할 안에서의 작업 방식 정의

### 패턴 3: Hook + Agent

```
Hook: "PR 생성 시 자동 리뷰 요청"
Agent: "Code Reviewer" (독립적으로 리뷰)
```

→ 특정 시점에 다른 관점 강제 투입

### 패턴 4: 3개 조합

```
Agent: "Full-stack Developer"
Skill: "컴포넌트 기반 설계, 타입 안전성 중시"
Hook: "빌드 전 타입 체크, 테스트 실행"
```

→ 역할(Agent) + 작업방식(Skill) + 검증(Hook)

## 🚦 마이그레이션 가이드

### Skill → Hook으로 승격

```
Before (Skill):
"코드 작성 후 린트 돌리기"

After (Hook):
pre-commit: npm run lint --fix
```

**승격 기준**: 3회 이상 누락 발생 시

### Skill → Agent로 분리

```
Before (Skill):
"코드 리뷰 관점으로 재검토"

After (Agent):
Code Reviewer Agent (독립 실행)
```

**분리 기준**: 역할 충돌로 품질 저하 시

### Hook → Agent로 확장

```
Before (Hook):
post-save: "TODO 항목 추출"

After (Hook + Agent):
post-save: TODO Analyzer Agent 호출
→ Agent가 우선순위 판단 + 이슈 생성
```

**확장 기준**: 단순 실행을 넘어 판단이 필요할 때

---

## ✅ 체크리스트

새로운 기능을 만들 때:

**1단계: 필수성 판단**

- [ ] 안 하면 문제가 되는가? → Hook
- [ ] 하면 좋은 정도인가? → Skill

**2단계: 역할 판단**

- [ ] 기존 역할과 관점이 충돌하는가? → Agent
- [ ] 같은 역할 내 작업 방식인가? → Skill

**3단계: 복잡도 판단**

- [ ] 판단/분석이 필요한가? → Agent
- [ ] 단순 실행/검증인가? → Hook
- [ ] 가이드라인인가? → Skill

## 💭 추가 인사이트

포스팅에서 고민하신 **"분류 전담 에이전트"** 관련:

제 생각엔 이건 **Meta-Agent** 개념인 것 같습니다:

```
Meta-Agent: "Workflow Designer"
입력: 사용자 요구사항
판단:
  - 반복 발생 → Skill
  - 누락 방지 → Hook
  - 관점 분리 → Agent 추천
출력: 최적 구조 제안
```

개인 프로젝트라면 오버엔지니어링일 수 있지만, 팀이나 복잡한 프로젝트에서는 충분히 가치 있어 보입니다. 특히 CSP님처럼 HR 온톨로지 자동화 같은 복잡한 시스템을 설계하실 때는요.

다만 시작은 **단순하게**: 일단 다 Skill로 시작 → 누락되면 Hook으로 → 역할 충돌하면 Agent로 점진적 진화가 현실적일 것 같습니다.
