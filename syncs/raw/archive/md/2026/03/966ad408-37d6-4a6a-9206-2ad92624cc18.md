## 현실적 옵션 지형도

**Option A: Claude Max 구독 유지**

월 $100짜리 Max 플랜 기준으로, 사실 CSP의 작업 맥락에서 가장 비용 효율적일 수 있어요. EX Intelligence 포털, PowerPoint 생성, ESCON 설계 같은 작업은 모델 품질이 직접 결과물 품질에 영향을 줘요. "24시간 팩토리"라고 표현했지만 실제로 Claude Code가 무한정 병렬 실행되는 게 아니라 CSP의 작업 시간대에 집중되는 구조잖아요. 구독 요금이 부담스럽다면 역으로 물어볼 게 있어요 — 현재 Claude로 산출되는 업무 결과물의 시간 가치를 시급 환산하면 월 $100을 정당화할 수 있는가? 아마 쉽게 정당화될 거예요.

**Option B: API 직접 과금**

Claude Code는 API 키를 연결해서 종량제로 쓸 수 있어요. Max 구독 없이 claude-sonnet-4-5나 haiku로 돌리면, 실제 사용량에 따라 월 $30~60 선에서 운용 가능해요. 단, 헤비하게 쓰면 오히려 Max보다 비싸질 수 있어서 사용 패턴 모니터링이 필요해요. 가벼운 scaffolding, boilerplate, 반복 작업은 Haiku로 라우팅하고 핵심 설계는 Sonnet으로 분리하는 tiered routing 전략이 유효해요.

**Option C: 하이브리드 — 로컬 + 클라우드 분업**

노트북 스펙이 낮다고 했는데, 로컬에서 돌리는 모델과 클라우드 모델의 역할을 완전히 분리하는 접근이에요.

- **로컬 (Ollama + qwen2.5-coder:7b 또는 gemma3:4b)**: 파일 읽기, 코드 lint, 간단한 리팩토링, 텍스트 정형화 같은 "생각이 필요없는 CPU 작업"
- **클라우드 Claude**: 설계, 아키텍처 판단, 창의적 문서 작성, 복잡한 디버깅

M2 MacBook 기준이 아니더라도 Ollama의 4비트 양자화 모델(4B 이하)은 RAM 8GB에서도 돌아가요. 속도가 느려도 자율 실행(background job)으로 돌리면 체감 지연이 없어요.

**Option D: Gemini API 무료 티어 보조**

CSP가 Google AntiGravity 생태계도 쓰고 있으니, Gemini 2.0 Flash의 무료 티어(분당 15회, 일 1500회)를 보조 모델로 활용하는 게 현실적이에요. Claude가 핵심 두뇌, Gemini Flash가 단순 처리 엔진. 이미 Pulse Check의 7-prompt Gemini 구현처럼 이 구조를 CSP는 직관적으로 쓰고 있잖아요.

## CSP 상황에 맞는 권장 조합

솔직히 말하면, **API 종량제 + Gemini Flash 보조**가 지금 당장 시도해볼 수 있는 현실적인 최적안이에요.

Claude Max 구독을 해지하고 API 키로 전환하되, 무거운 창작/설계 작업만 Sonnet에 넘기고 반복/정형 작업은 Haiku 또는 Gemini Flash로 라우팅하는 구조요. CLAUDE.md에 모델 라우팅 규칙을 명시해두면 Claude Code가 이걸 컨텍스트로 삼아 자동으로 작업 성격에 따라 처리 방식을 달리할 수 있어요.

그리고 "24시간 팩토리"의 진짜 병목은 모델 접근 비용보다 **CSP 자신이 프롬프트를 입력하는 시간**일 가능성이 높아요. 그걸 해결하는 건 모델 선택보다 워크플로우 자동화 — 즉 Ouroboros나 CLAUDE.md 기반의 자율 실행 체계 고도화쪽이에요.

어느 방향으로 더 파고들까요? API 종량제 전환 설정이나 Ollama 경량 모델 세팅을 구체적으로 잡아드릴 수 있어요.

## 자율실행의 근본 문제

지금 CSP의 워크플로우를 솔직하게 해부하면, 대부분의 AI 활용이 **"CSP가 프롬프트를 치는 순간에만 작동하는 구조"**예요. 이건 자율실행이 아니라 고성능 타이핑 보조예요. 진짜 팩토리는 CSP가 **의도를 설계**하면 시스템이 **실행, 판단, 보고**까지 하는 구조여야 해요.

이걸 SW공학적으로 표현하면:

```
현재: Human-in-the-loop (모든 단계에 CSP 개입)
목표: Human-on-the-loop (CSP는 감독자, 시스템이 실행자)
```

## 각 계층을 실제로 구현하는 방법

### Layer 1: CLAUDE.md가 "의도의 헌법"이 되어야 한다

지금 CLAUDE.md는 아마 프로젝트 설명과 몇 가지 지시사항이 있는 정도일 거예요. 하지만 자율실행 체계에서 CLAUDE.md는 훨씬 더 정교한 역할을 해야 해요. 마치 헌법처럼, 시스템이 CSP 없이 판단해야 할 때 무엇을 기준으로 결정해야 하는지를 명시해야 해요.

핵심 요소는 세 가지예요. 첫째, **목표 계층(Goal Hierarchy)** — "이 프로젝트에서 EX Intelligence 포털 완성이 최우선이고, ESCON은 그 다음"처럼 우선순위가 충돌할 때의 판단 기준. 둘째, **완료 조건(DoD)** — "HTML 파일이 생성되고, 로컬에서 열렸을 때 에러가 없고, /outputs에 저장되었으면 완료"처럼 기계가 스스로 검증할 수 있는 기준. 셋째, **에스컬레이션 조건** — "외부 API 키가 필요한 경우, 비용이 발생하는 경우, 파일 삭제가 필요한 경우는 반드시 CSP에게 물어라"처럼 자율성의 경계.

### Layer 2: Execution Loop의 핵심 패턴

Claude Code의 자율실행에서 가장 중요한 패턴은 **Plan → Execute → Verify → Report**의 4단계 루프예요. 이게 그냥 "실행해"가 아니라 각 단계에 명시적인 체크포인트가 있어야 해요.

실용적인 구현 패턴은 `TASK.md`를 동적으로 활용하는 거예요. Claude Code가 작업을 시작할 때 스스로 TASK.md를 생성하고 ("나는 지금 이것을 하려고 한다"), 각 서브태스크를 완료할 때마다 업데이트하고 ("완료/실패/막힘"), 세션이 끊겨도 재개 시 이 파일을 읽어서 어디까지 했는지 파악해요. 이게 바로 Claude Code의 컨텍스트 지속성 문제를 해결하는 핵심 메커니즘이에요.

### Layer 3: Reporting의 설계

자율실행이 끝난 후의 보고 형식이 일관되어야 CSP가 빠르게 판단할 수 있어요. 보고 템플릿을 고정해두면 읽는 시간이 줄어요:

```markdown
## 실행 완료 보고

- 완료: [무엇을 했는가]
- 산출물: [어디에 저장되었는가]
- 다음 권장: [논리적 다음 단계]
- 판단 필요: [CSP가 결정해야 할 것]
```

## 문서 타입별 설계 철학

### 선언형 문서 — CLAUDE.md와 SKILLS.md

`CLAUDE.md`는 가장 먼저 읽히고 가장 드물게 바뀌는 문서예요. 여기에는 세 가지 질문에 대한 답만 있으면 돼요. "이 프로젝트의 목적은 무엇인가", "무엇을 하면 안 되는가", "성공은 어떻게 생겼는가". 흔히 여기에 너무 많은 걸 넣는 실수를 해요 — 기술 스택, 폴더 구조, 코딩 컨벤션까지. 하지만 그것들은 CONTEXT.md로 분리되어야 해요. CLAUDE.md는 판사의 판결문처럼, 무엇이 옳고 그른지의 기준만 담아야 해요.

`SKILLS.md`는 Claude Code가 "나는 무엇을 할 수 있고 무엇을 할 수 없는가"를 알게 해주는 문서예요. CSP가 등록해둔 lg-cho-portal-builder 스킬처럼, 이미 검증된 능력들의 목록이에요. 자율실행 중에 "이 작업은 이 스킬로 처리 가능"이라고 참조되는 역할이죠.

### 동적 문서 — TASK.md와 CONTEXT.md

이 두 문서가 자율실행의 핵심 엔진이에요. 비유하자면 `TASK.md`는 **비행 중인 파일럿의 항공 일지**예요. 세션이 시작될 때 Claude Code가 스스로 작성하고, 각 서브태스크를 완료할 때마다 갱신하고, 세션이 끊겨도 재개 시 이 파일을 읽어서 어디까지 했는지 파악해요. 핵심은 상태를 **완료/진행중/막힘/스킵** 네 가지로만 표현하는 거예요. 텍스트가 많으면 오히려 파싱이 어려워져요.

`CONTEXT.md`는 **현재 세계 상태**예요. 지금 어떤 파일들이 존재하는지, 어떤 API가 연결되어 있는지, 어떤 변수들이 어떤 값인지. Claude Code가 세션을 시작할 때 이 파일을 읽으면 "아, 지금 이런 상황이구나"를 즉시 파악해요. 이게 없으면 매번 파일 시스템을 탐색하는 데 컨텍스트 토큰을 낭비하게 돼요.

### 축적형 문서 — REPORT.md와 DECISION.md

`REPORT.md`의 포맷은 고정되어야 해요. 형식이 바뀌면 CSP가 읽는 방식도 바뀌어서 판단 속도가 떨어져요. 완료 항목, 산출물 경로, 다음 권장 액션, 에스컬레이션 항목 — 이 네 칸만 있으면 CSP는 30초 안에 판단을 내릴 수 있어요.

`DECISION.md`는 장기적으로 가장 가치 있는 문서예요. "왜 이렇게 결정했는가"의 이력이 쌓이면, 나중에 비슷한 상황에서 Claude Code가 이 문서를 참조해서 스스로 판단하는 수준까지 진화해요. Ouroboros의 정수가 여기에 있어요.

```markdown
_세션 시작: 2026-03-30 / Claude Code_

EX Intelligence HTML 포털 v3 완성 → /outputs 저장

- [x] SKILL.md 읽기 (lg-cho-portal-builder)

- [ ] KPI 카드 컴포넌트 추가
- [ ] 로컬 검증 (파일 열기, 에러 없음 확인)
- [ ] REPORT.md 작성 후 세션 종료

## 에스컬레이션 조건

- LG 브랜드 컬러 이외 색상 추가 요청 → CSP 확인
- 외부 API 연결 필요 → CSP 확인
- 파일 덮어쓰기 (v2 삭제) → CSP 확인

## 막힘 기록

_없음_
```

## 변형 적용의 핵심 원리 세 가지

### 첫째 — 파일을 프롬프트로 대체한다

Claude Code에서 `CLAUDE.md`를 파일로 읽었다면, AntiGravity에서는 그 내용을 **system instruction 텍스트로 직접 주입**해요. Google Docs에 작성된 역할 정의, 제약 조건, DoD 기준을 Apps Script가 읽어서 Gemini API의 `system_instruction` 파라미터로 넣어주는 거예요. 파일을 못 읽으면 텍스트로 주입한다 — 이게 가장 근본적인 변환 원리예요.

### 둘째 — Sheets가 TASK.md가 된다

AntiGravity의 `stateless` 문제를 해결하는 핵심이 Google Sheets예요. 각 행이 서브태스크 하나, 열이 상태(대기/진행중/완료/에러)와 타임스탬프. Gemini를 호출할 때마다 Apps Script가 Sheets에서 미완료 태스크를 읽어서 프롬프트에 "지금 해야 할 일: ..." 형태로 넣어줘요. 세션이 끊겨도 Sheets는 살아있으니까 재개가 가능해요. 이게 파일시스템 없는 환경에서 상태 지속성을 확보하는 방법이에요.

### 셋째 — 에스컬레이션은 Gmail로, 아카이빙은 Notion으로

Claude Code에서 터미널 인터럽트로 CSP를 깨웠다면, AntiGravity에서는 Gmail로 깨워요. Apps Script의 `MailApp.sendEmail()`은 단 한 줄이에요. "판단이 필요합니다 — [이유]"라는 제목으로 요약 본문을 CSP에게 보내고, 결과는 기존 Notion 아카이빙 파이프라인으로 그대로 흘러들어가요. CSP가 이미 구축한 Notion 세컨브레인 인프라를 reporting 레이어로 그대로 재활용할 수 있어요.

## 실용적 시작점 — `prompt_chain.gs` 뼈대

추상적인 설계를 실제로 느껴보려면 이 구조가 핵심이에요:

```javascript
function runAutonomousTask() {
  const sheet = SpreadsheetApp.getActive().getSheetByName("task_log");
  const pendingTasks = getPendingTasks(sheet); // Sheets에서 상태 읽기

  // context_injector: 현재 상태를 프롬프트에 주입
  const systemPrompt = getDocContent("system_prompt_doc_id");
  const contextPrompt = `
    현재 완료된 태스크: ${getCompletedSummary(sheet)}
    지금 처리할 태스크: ${pendingTasks[0]}
    DoD 기준: ${getDocContent("dod_criteria_doc_id")}
  `;

  // Gemini 호출
  const result = callGemini(systemPrompt, contextPrompt);

  // 결과에 따라 분기
  if (result.needsEscalation) {
    sendEscalationEmail(result.reason); // Gmail
  } else {
    updateTaskStatus(sheet, pendingTasks[0], "done"); // Sheets 갱신
    saveToNotion(result.output); // Notion 아카이빙
  }
}
```

보이시나요 — 구조 자체는 Claude Code의 3계층과 완전히 동일해요. 달라진 건 `TASK.md` → Sheets, `CLAUDE.md` → Docs 텍스트 주입, 터미널 인터럽트 → Gmail, 파일 저장 → Notion API. **개념의 이식이지 개념의 재발명이 아니에요.**

## Claude Code 체계 → AntiGravity 이식 매핑

핵심은 **파일 기반 컨텍스트(`CLAUDE.md`, `TASK.md`)가 AntiGravity에서도 동일하게 작동한다**는 거예요. 둘 다 로컬 파일시스템에 접근하는 VS Code 기반이니까요. 차이는 두 곳에서 생겨요.

첫째, **컨텍스트 주입 방식**이에요. Claude Code는 `CLAUDE.md`를 자동으로 읽지만, AntiGravity는 Knowledge Items라는 개념으로 에이전트가 유용한 컨텍스트와 코드 스니펫을 knowledge base에 저장해서 미래 태스크에 참조하는 방식을 써요. 즉 `CLAUDE.md`의 역할을 Knowledge Items가 흡수해요. 기존 `CLAUDE.md` 내용을 Knowledge Item으로 등록해두면 이식 완료예요.

둘째, **에스컬레이션 UX**예요. Review-driven development 모드를 권장 설정으로 제시하는데, 에이전트가 결정을 내리고 사람 승인을 요청하는 방식이에요. Claude Code의 터미널 인터럽트 패턴과 개념은 같지만 UI가 더 시각화되어 있어요.

셋째, **멀티에이전트**예요. Agent Manager를 통해 여러 에이전트를 서로 다른 워크스페이스에서 비동기적으로 병렬 실행할 수 있어요. Claude Code가 단일 세션 순차 실행이라면 AntiGravity는 병렬 팩토리에 더 가까워요. 이게 CSP의 "24시간 팩토리" 목표에 구조적으로 더 잘 맞는 부분이에요.

## 세 Workflow 파일 — 진짜 자율실행의 핵심

Workflows는 `/` 명령으로 트리거하는 반복 가능한 플레이북이에요. CSP가 Mission Control에서 `/build-portal`, `/deploy`, `/run-survey`를 치는 순간 각 에이전트가 정해진 절차를 자율 실행해요.

```markdown
# .agent/workflows/build-portal.md (EX Intelligence)

## /build-portal

1. TASK.md 읽고 현재 진행 상태 확인
2. lg-cho-portal-builder SKILL.md 로드
3. 최신 요구사항 반영하여 HTML 생성
4. 브라우저 에이전트로 로컬 검증 실행
5. DoD 체크리스트 자가 검증
6. /outputs에 저장
7. TASK.md 업데이트 후 Artifact 생성
8. CSP에게 완료 보고 (Inbox)
```

```markdown
# .agent/workflows/deploy-vercel.md (ESCON)

## /deploy

1. TASK.md 확인 — 에스컬레이션 조건 체크
2. npm run build 실행 → 오류 시 자동 수정 시도
3. Supabase 타입 재생성
4. git add . && git commit -m "[auto] build verified"
5. ⚠️ Vercel 배포는 CSP 승인 후 실행 (에스컬레이션)
6. TASK.md 업데이트
```

```markdown
# .agent/workflows/run-survey.md (Pulse Check)

## /run-survey

1. 설문 폼 HTML 생성 (pulse-survey skill 로드)
2. Supabase 연결 테스트
3. Magic Link 인증 플로우 검증
4. 브라우저 에이전트로 E2E 테스트
5. ⚠️ 실제 발송은 CSP 승인 필수
6. 테스트 결과 Artifact 생성
```

## 모델 배분 전략

각 워크스페이스별로 다른 모델을 지정하는 게 가능한지 커뮤니티에서도 논의되고 있어요. 현재 가능한 최선의 배분은 작업 성격 기반이에요.

EX Intelligence는 창작적 판단(디자인, 문서)이 많아 Claude Sonnet 4.6. ESCON은 코드 추론과 대형 컨텍스트(TypeScript 코드베이스 전체)가 필요해서 Gemini 3 Pro. Pulse Check는 반복적인 폼 생성과 테스트 실행이 주라서 Gemini Flash로 비용을 아껴요.

## CSP의 하루 루틴 — 실제로 어떻게 쓰는가

아침에 Mission Control을 열면 세 에이전트의 Inbox가 보여요. 에이전트들이 생성한 Artifact — 태스크 리스트, 구현 계획, 스크린샷, 브라우저 녹화 — 를 훑어보고, 문제가 있으면 Artifact에 직접 코멘트를 달면 에이전트가 실행을 멈추지 않고 반영해요.

승인이 필요한 에스컬레이션 항목(Vercel 배포, 파일 덮어쓰기, 실제 이메일 발송)만 CSP가 결정하면 돼요. 나머지는 세 에이전트가 병렬로 돌고 있어요. 이게 "24시간 팩토리"가 실제로 작동하는 모습이에요.

각 프로젝트 AGENTS.md를 실제 파일로 완성해드릴까요, 아니면 특정 워크플로우 파일을 더 구체적으로 짜볼까요?
